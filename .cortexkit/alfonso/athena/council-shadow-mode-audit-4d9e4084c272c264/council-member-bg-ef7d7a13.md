# Blind Adversarial Audit — Magic Context Shadow Mode

**False-positive filtering performed:** I read the actual TS builders (`shadow-sender.ts`), every Rust wire struct + handler (`mc-module/src/lib.rs`), the store CAS (`mc-store/src/lib.rs`), both ordinal readers (`read-session-raw.ts`), the enqueue call site (`transform.ts`), the shadow unit tests (`shadow-sender.test.ts`), the sole Rust integration test (`real_daemon.rs`), and `pi-plugin/PARITY.md`. I confirm there is **no `#[serde(flatten)]`, alias, or `deny_unknown_fields`** on the wire structs, and I checked which shapes the tests actually assert before claiming each bug.

---

## Finding 1: Compartment wire-shape mismatch — every state_sync carrying a compartment is rejected by Rust serde
- **Severity**: CRITICAL
- **Location**: `shadow-sender.ts:584-615` (`serializeCompartment`) vs `crates/mc-module/src/lib.rs:266-295` (`ShadowCompartmentWire`)
- **Confidence**: high
- **Issue**: This is the SAME bug class as the two already-fixed integration bugs (wire-shape), still live for compartment inner fields. TS emits each compartment as **nested** objects:
  ```
  { id, sequence, start:{flat_id, bare_message_id, absolute_ordinal}, end:{...}, title, content, ... }
  ```
  But `ShadowCompartmentWire` declares `start_message: i64` and `end_message: i64` as **required, non-defaulted** flat fields (lib.rs:269-270 — no `#[serde(default)]`). The TS payload contains no top-level `start_message`/`end_message`; the nested `start`/`end`/`id` objects are silently ignored (no `deny_unknown_fields`), and serde then fails with *"missing field `start_message`"*. `handle_shadow_state_sync_value` (lib.rs:2149-2151) returns `invalid_params_error` and the whole state_sync rejects.
- **Blast radius**: Any session that has ever formed a compaction boundary (i.e. every real long session — the soak's entire target population) sends ≥1 compartment in state_sync (`buildStateSyncPayload` line 646-657), so **state_sync rejects on every pass**, and because `processPass` calls state_sync *before* the transform (line 986-1007), `shadow_transform` is never reached. The reject code `invalid_params` is neither a peer-reject nor a connection failure, so the TS side merely does `send_failures += 1` + "send failed (ignored)" (runQueue line 889-904) and retries forever. Net effect: **the soak produces zero valid comparisons for any compartmentalized session** — it silently validates nothing while looking healthy. Class (2), defeats the soak's purpose.
- **Evidence — why the mocks miss it**: `shadow-sender.test.ts:350-390` builds state_sync from `basePass` with a **fresh DB and no compartments inserted**, then asserts only `compartments: expect.any(Array)` — it never populates a compartment nor cross-checks the inner shape against the Rust struct. `real_daemon.rs:300-316` constructs `StoredCompartment` **directly in Rust** and calls `replace_compartments`, bypassing the JSON wire entirely. Neither side ever sends a populated compartment across the wire. Exactly the gap the prompt warned about.
- **Suggested Fix**: Make `ShadowCompartmentWire` parse the nested `start`/`end` objects (custom deserialize or a nested `ShadowCompartmentEdgeWire { flat_id, bare_message_id, absolute_ordinal }`), OR have TS emit flat `start_message`/`end_message`. Then add an end-to-end test that serializes a real populated compartment through `toFlatWireBody` and deserializes it with `serde_json::from_value::<ShadowStateSyncWire>` in a shared fixture.

## Finding 2: `m0_mutations` (and `watermarks`) silently dropped at the Rust parser
- **Severity**: HIGH
- **Location**: `shadow-sender.ts:732,735` (emits `params.watermarks`, `params.m0_mutations`) vs `ShadowStateSyncWire` (lib.rs:185-200)
- **Confidence**: high (drop is certain); medium (functional impact magnitude)
- **Issue**: TS sends `m0_mutations` (from `getM0MutationsAfterId`, line 696-706) and `watermarks` (line 732) in state_sync. `ShadowStateSyncWire` has **no `m0_mutations` field and no `watermarks` field** — only `acked_watermarks: Option<Value>` (default). With no `deny_unknown_fields`, both are **silently discarded**. Grep for `m0_mutations` across `crates/mc-module/src` returns **0 matches**, and `reset_shadow_session` (lib.rs:2207-2226) deletes `shadow_memories` and `shadow_memory_mutation_log` but has **no shadow m0-mutation table** — so the Rust side neither receives nor models m0 mutations. The module's shadow transform therefore materializes m[0] without the m0 mutation inputs the live TS lane applied.
- **Blast radius**: On sessions *without* compartments (where Finding 1 doesn't yet fire), every m0-mutation-bearing pass (todo state changes etc.) will produce a **systematic m[0] byte divergence** whose root cause is missing input, not a real transform bug — poisoning the soak's divergence signal with false positives (or masking real ones). Class (2), corrupts shadow comparison silently. The `watermarks` drop is benign (Rust recomputes `acked_watermarks` at lib.rs:2176-2183), but the `m0_mutations` drop is functional.
- **Suggested Fix**: Either add `m0_mutations` to `ShadowStateSyncWire` + a shadow m0 table + reset cleanup, or (if m[0] is intentionally recomputed from compartments only) stop sending `m0_mutations` and document that m[0] divergences from m0 activity are expected/excluded from the compare.

## Finding 3: Ordinal-basis mismatch between tail-primed cache and the by-id COUNT fallback under below-boundary deletion
- **Severity**: MEDIUM-HIGH
- **Location**: `shadow-sender.ts:375-406` (`resolveOrdinalsForShadow`), `read-session-raw.ts:106-117` (full/tail reader, `index+1`) vs `read-session-raw.ts:384-393` (`readRawSessionMessageByIdFromDb`, `COUNT(*)`)
- **Confidence**: medium
- **Issue**: In steady state the two bases agree: full/tail reader assigns `ordinal = index+1` over filtered non-summary rows sorted `(time_created, id)`, and the by-id `COUNT(*) WHERE …(tc<? OR (tc=? AND id<=?))` equals that same count — verified equivalent. **However**, the tail-primed cache (`readRawSessionTailFromDb`, line 158-239) sets absolute ordinals from `baseOrdinal = lastCompartmentEnd` (the *stored compaction marker ordinal*), while the by-id fallback computes the ordinal **fresh from current DB state**. If any non-summary row **below the boundary is deleted** after the marker was written (e.g. an OpenCode message revert/undo), the marker's `baseOrdinal` goes stale: above-floor messages (served from the tail cache) carry stale-basis ordinals while below-floor messages (served by the by-id COUNT) carry fresh-basis ordinals — **mixed bases within a single pass**. The memo drift check (line 400-402) only compares an id against its own prior value across passes; it cannot detect intra-pass cross-message inconsistency. Result: wrong absolute ordinals written to the shadow store → corrupt shadow lineage that emits false divergences.
- **Blast radius**: Class (2), silent shadow corruption. Reachability is conditional (requires the tail-primed cache to be active during `enqueue` AND a below-boundary deletion). I could not confirm the transform's `withRawSessionMessageCache` scope wraps the `enqueue` call (grep found no `withRawSessionMessageCache` in `transform.ts`), which is why confidence is medium — but the shipped comment at `shadow-sender.ts:386-394` explicitly asserts the tail-only-prime scenario is real for this function, so the code itself claims the risky path exists.
- **Suggested Fix**: Have the fallback derive ordinals on the **same basis** as the primed cache (anchor the by-id COUNT to `baseOrdinal` + relative offset from the marker anchor), or invalidate/refuse the tail-prime basis when the marker ordinal cannot be reconciled with a fresh boundary COUNT (fail loud → reset, rather than emit mixed ordinals).

## Finding 4: Shadow mode adds 3 synchronous full-array JSON deep-clones to the LIVE transform path
- **Severity**: HIGH
- **Location**: `transform.ts:459` (`cloneForShadow(messages)`), `shadow-sender.ts:380` (`cloneJson(args.messages)` in `resolveOrdinalsForShadow`), `shadow-sender.ts:288` (`cloneJson(args.outputMessages)` in `denormalizeShadowOutput`)
- **Confidence**: high (clones exist and run inline); medium (ms magnitude)
- **Issue**: The design states the soak is "without affecting the live session," but with `shadow_transform.enabled`, each transform pass runs, **synchronously on the user's critical path**: (1) `cloneForShadow(messages)` at the top of the transform (line 459) capturing the pre-mutation snapshot, then in `enqueue` (line 2205, which runs inside the transform before it returns) (2) `cloneJson(inputMessages)` and (3) `cloneJson(outputMessages)`. Each is a `JSON.parse(JSON.stringify(...))` round-trip over the **entire** message array. On a 400-message tool-heavy session these arrays are multi-MB; three full round-trips per pass is tens-to-hundreds of ms added to the live prompt latency. The `enqueue` clones are inside a try/catch (line 2226) so they are *throw*-safe, but not *cost*-bounded. `cloneForShadow` at line 459 is **outside** that try/catch.
- **Blast radius**: Class (1) — directly affects live user latency, contradicting the "observe-only, no live impact" contract. Not a correctness bug for the live output, but the worst-weighted class because it touches the live session.
- **Suggested Fix**: Defer/observe the clones off the hot path (structured-clone the input once, hand it to the async queue, and clone the output lazily inside `runQueue` rather than in `enqueue`), or gate the capture behind a size cap and drop (with a counter) above it. Measure per-pass added latency on a large session before arming production.

## Finding 5: Cross-lane coupling via the shared store handle and shared std::Mutexes
- **Severity**: MEDIUM
- **Location**: `handle_shadow_transform_value` (lib.rs:2250-2438) using the shared `Arc<McStore>` + `self.bindings.lock().expect(...)` (lib.rs:790), `with_conn_fenced` in `apply_shadow_state_sync`/`reset_shadow_session`
- **Confidence**: medium
- **Issue**: Every real transform in the soak mirrors a `shadow_transform` that runs `transform_with_projection` + `record_shadow_report`/`record_shadow_divergence` against the **same** `McStore` connection (serialized by `with_conn_fenced`) and takes the **same** `self.bindings` / store std::Mutexes the real lane uses. Two coupling risks: (a) DB-lock **contention** — shadow store ops add fenced-connection hold time that can delay real-lane store ops (latency only, short-held). (b) **Mutex poisoning** — the handler uses `.expect("… mutex")` on shared `std::sync::Mutex`es; a panic in shadow-path code while holding a shared lock would poison it, and the next real-lane `.lock().expect(...)` would then panic too. The compare path (`compare_shadow_outputs`, line 2407) runs outside the store txn, and rusqlite is Result-based, so a panic is low-probability — but the poison path is a genuine cross-lane blast channel that the "observe-only" framing assumes cannot exist.
- **Blast radius**: Class (1) if a poison ever triggers; otherwise class (3) latency. Preserve as a concern rather than dismiss.
- **Suggested Fix**: Ensure no shadow code path can panic while holding a mutex shared with the real lane (replace `.expect` with poison-tolerant recovery or `parking_lot` non-poisoning mutexes for the shared bindings), and consider a separate store connection/handle for the shadow lane.

## Verified GOOD (false-positive filter — not findings)
- **Isolation (3a)**: `shadow_binding` (lib.rs:807-812) rejects non-shadow bindings for shadow ops; `ctx_reduce` (lib.rs:1711-1716) and plain `transform` (lib.rs:1944-1950) reject shadow bindings — enforced on every arm. Shadow writes are namespaced by `shadow:` session_id and `shadow_project_path`, and shadow rows live in separate tables (`shadow_memories`, `shadow_memory_mutation_log`) except `mc_compartments`/`pending_agent_drops` which are keyed by the prefixed session_id. String-exact session_id keying keeps lanes disjoint. Confidence high.
- **CAS (3c)**: `apply_shadow_state_sync` gates on `shadow_generation` and `expected_shadow_seq` (lib.rs:2111-2120) inside `with_conn_fenced`; the flat `shadow_generation`/`expected_shadow_seq` ARE sent correctly by `toFlatWireBody`, so the generation/seq CAS works. Compartment upserts are keyed by `(session_id, sequence)` so overlapping sequences are idempotent-upsert, not duplicating.
- **enqueue throw-safety (2a)**: the `enqueue` call is wrapped in try/catch at `transform.ts:2226`, so a throw inside `resolveOrdinalsForShadow`/`denormalizeShadowOutput`/`cloneJson`/the by-id DB read (incl. SQLITE_BUSY) is caught and the live pass proceeds. Live correctness is protected against shadow throws (the remaining live exposure is cost, Finding 4, and the unguarded `cloneForShadow` at line 459).
- **Frame/reader sync (2d)**: corr+channel matching in `readTerminalFor` (line 1392-1405) with full length-prefixed frame reads means a late response after a 5s timeout is fully consumed and discarded by the next call — the stream stays aligned, no permanent wedge. `pending` chain serializes calls correctly. Queue transitions (`blockedUntilReset`/`requireResetReason`) self-heal on the next enqueue via `processPass`→`performReset` (line 952-959).

## Summary
**Findings: 1 Critical, 2 High, 1 Medium-High, 1 Medium.**

- **Critical (1)**: Nested-compartment wire shape rejects at Rust serde — the exact wire-shape bug class already burned twice — silently zeroing the soak's comparison coverage for every compartmentalized (i.e. every real target) session.
- **High (2)**: Shadow mode adds 3 synchronous full-array JSON clones to the live path (violates "no live impact"); `m0_mutations` silently dropped at the parser (poisons the divergence signal with false positives).
- **Medium-High (1)**: Tail-prime vs by-id ordinal basis can mix within a pass after a below-boundary deletion, corrupting the shadow lineage silently.
- **Medium (1)**: Shared store handle + shared std::Mutex create a cross-lane latency/poison channel.

**Verdict: HOLD.**

**Single most important reason**: Finding 1 (compartment wire-shape mismatch) is the same class of wire-shape defect that the first armed run already exposed, still uncaught by the mocks, and it causes **every state_sync carrying a compartment to reject at the Rust serde layer** — so arming the soak on production sessions would produce zero valid parity comparisons for the exact population the gate exists to validate, while the dashboards show only generic "send failed" noise. The soak would certify parity it never actually measured. Fix Finding 1 (and re-test with a real populated compartment crossing the JSON wire in a shared TS↔Rust fixture), triage Findings 2 and 4, before arming.
