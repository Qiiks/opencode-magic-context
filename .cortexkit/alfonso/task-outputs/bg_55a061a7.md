## Finding 5: Wrapup vs in-flight historian lease interplay is safe (lease is cross-process, BEGIN IMMEDIATE check-then-publish), but wrapup-vs-wrapup rejection has NO existing race-free guard
- **Severity**: HIGH
- **Location**: `packages/plugin/src/hooks/magic-context/compartment-runner.ts:100-167` (`startCompartmentAgent` — check-then-set in single-threaded event loop); `compartment-lease.ts:13-38` (`acquireCompartmentLease` — cross-process DB lease); `compartment-runner-incremental.ts:606-616` (`isCompartmentLeaseHeld` under `BEGIN IMMEDIATE`)
- **Confidence**: high
- **Issue**: (a) Wrapup vs in-flight background historian: SAFE. The DB lease (`compartment-lease.ts:13-38`) is a single-row per-session `INSERT … ON CONFLICT DO UPDATE … WHERE holder_id = excluded.holder_id OR expires_at <= now`. If a background historian holds the lease, wrapup's `acquireCompartmentLease` returns null → wrapup must wait (spec says "wait for it"). The publish path re-checks `isCompartmentLeaseHeld` under `BEGIN IMMEDIATE` (`:606-616`) so a lease-lost publish rolls back. (b) Wrapup vs wrapup: the spec says "reject the second invocation." There is NO existing wrapup-vs-wrapup guard because the command does not exist yet. The `activeRuns` map (`compartment-runner.ts:30`) is process-local and keyed by sessionId — a second wrapup calling `startCompartmentAgent` would hit the `existing` check at `:104-107` and return early (no new run started), but the spec wants a REJECTION (user-facing error), not a silent no-op. More importantly, `activeRuns` is process-local: two PROCESSES running wrapup concurrently would both pass the `activeRuns.get` check and both attempt `acquireCompartmentLease` — one wins the lease, the other gets null and must back off. The lease IS the race-free cross-process authority. But the spec's "reject the second invocation" needs an explicit wrapup-level guard (e.g., a `wrapup_in_progress` session_meta flag set under `BEGIN IMMEDIATE`) to give the second caller a clean rejection message rather than a lease-denied retry loop. (c) Wrapup vs /ctx-recomp: recomp clears the injection cache eagerly (`compartment-runner-recomp.ts:265-267`, `:567-568`) and CAS-clears stale pending markers (`:326-331`); wrapup preserves the cache. If recomp runs mid-wrapup, recomp's `DELETE FROM compartments` (`:110`) + marker update would DESTROY wrapup's in-progress published compartments and move the marker — wrapup's next iteration would re-resolve from a wiped state. The lease prevents concurrent execution (both take the same per-session lease), so this is safe IF wrapup holds the lease for the ENTIRE loop (not per-iteration). The spec must specify that wrapup acquires the lease ONCE for the whole loop, not per `runCompartmentAgent` call (each `startCompartmentAgent` call acquires+releases its own lease at `:110`/`:147`). (d) Wrapup loop in progress when ≥95% emergency arm fires: the emergency arm calls `startCompartmentAgent` (`transform-compartment-phase.ts:336`), which hits the `existing` check at `compartment-runner.ts:104` and returns early (no duplicate run) — SAFE for in-process. Cross-process, the lease prevents collision.
- **Evidence**: `startCompartmentAgent` check-then-set at `:104-107` (process-local only); lease at `compartment-lease.ts:13-38` (cross-process); recomp's `DELETE FROM compartments` at `compartment-runner-recomp.ts:110`; each `startCompartmentAgent` acquires+releases its own lease (`:110`, `:147`).
- **Suggested Fix**: (1) Add a `wrapup_in_progress` session_meta flag set under `BEGIN IMMEDIATE` for race-free cross-process rejection. (2) Specify that wrapup holds the compartment lease for the ENTIRE loop (re-acquiring per iteration creates a window where recomp can grab the lease between iterations and wipe compartments). (3) Reject /ctx-recomp while wrapup is active and vice versa.

## Finding 6: No-op guard "tail already within keep-N" must count MEANINGFUL messages newest-first, but `getRawHistoryEligibility` counts ALL raw messages — the spec's counting rule is not directly available
- **Location**: `packages/plugin/src/hooks/magic-context/protected-tail-boundary.ts:657-672` (`getRawHistoryEligibility` — counts `rawMessageCount`, not meaningful); `read-session-formatting.ts:28-45` (`hasMeaningfulUserText`); `protected-tail-boundary.ts:497-509` (meaningful-user floor loop)
- **Confidence**: medium
- **Issue**: The spec says "The keep watermark counts MEANINGFUL messages newest-first." `getRawHistoryEligibility` (`:657-672`) returns `rawMessageCount` = total raw messages (including tool-only, ignored, system-directive-only). The meaningful-user counting logic (`hasMeaningfulUserText` at `read-session-formatting.ts:28-45`) is used inside `resolveProtectedTailBoundary` for the live-prompt floor (`:497-509`) but is NOT exposed as a standalone "count meaningful messages above ordinal X" helper. The wrapup no-op guard ("tail already within keep-N") needs to count meaningful messages from `lastCompartmentEnd+1` to `rawMessageCount` newest-first, then snap outward per arc rule. There is no existing helper that does exactly this — the boundary's `semanticSnapBoundary` (`:243-258`) snaps to semantic candidates but does not COUNT to a target N. The spec must implement a new counter. If it naively uses `rawMessageCount - offset <= N`, it will false-positive no-op on tool-heavy tails (many non-meaningful messages) and false-negative on user-heavy tails. The arc-fencing (`fenceBoundaryForToolArcs` at `read-session-true-raw-tokens.ts:470-504`) is available for the outward snap.
- **Evidence**: `getRawHistoryEligibility` returns raw count (`:665`); `hasMeaningfulUserText` is the meaningful filter but no "count meaningful above ordinal" helper exists; `semanticSnapBoundary` snaps but does not count to a target.
- **Suggested Fix**: Implement a dedicated `countMeaningfulMessagesAboveOrdinal(db, sessionId, ordinal)` helper reusing `hasMeaningfulUserText`, then apply `fenceBoundaryForToolArcs` for the outward snap. Do not reuse `getRawHistoryEligibility`'s raw count for the no-op guard.

## Finding 7: /ctx-flush does NOT apply wrapup output — it only drops pending tag ops; the spec's "/ctx-flush suggestion" is misleading unless the deferred marker has already moved
- **Severity**: MEDIUM
- **Location**: `packages/plugin/src/hooks/magic-context/execute-flush.ts:10-36` (`executeFlush` — only `getPendingOps` + `updateTagStatus` to "dropped"); `hook.ts:752-758` (`onFlush` signals `historyRefreshSessions` + `systemPromptRefreshSessions` + `pendingMaterializationSessions`); `transform-postprocess-phase.ts:1179-1214` (deferred marker drain requires `historyWasConsumedThisPass`)
- **Confidence**: high
- **Issue**: The spec implies the user can run /ctx-flush to materialize wrapup output. `executeFlush` (`execute-flush.ts:10-36`) does ONLY pending-op drops — it does NOT touch compartments or the compaction marker. The materialization path is `onFlush` (`hook.ts:752-758`) which signals the three refresh sets; the next transform pass then rebuilds history (`prepareCompartmentInjection`) and, IF `historyWasConsumedThisPass` (`transform-postprocess-phase.ts:1145-1150`) AND `deferredHistoryWasPendingAtPassStart`, drains the pending marker blob (`:1179-1214`). So /ctx-flush DOES trigger materialization on the NEXT pass — but only if a pending marker blob exists. If wrapup published 8 chunks and the last pending blob survived (Finding 3), /ctx-flush → next pass → drain applies the marker at the final ordinal → `filterCompacted` stops at the new boundary → raw tail above the boundary is excluded. This WORKS. The risk: if the user runs /ctx-flush BEFORE the wrapup's last publish has landed its pending blob (e.g., wrapup is still mid-loop), the flush's materializing pass may drain a STALE pending blob (from an earlier publish) — but `validatePendingTarget` (`compaction-marker-manager.ts:84-118`) catches this (`target-superseded` if ordinal differs) and CAS-clears, leaving the newer blob for the next pass. So this is self-healing. The real issue is UX honesty: /ctx-flush's user-facing message ("Flushed: N dropped. Changes take effect on next message.") does NOT mention compartment materialization — the user may not realize they need to send a message to trigger the materializing pass. The spec should clarify that /ctx-flush + a subsequent message applies the wrapup, OR that wrapup's materialization rides the NEXT NATURAL bust (no flush needed).
- **Evidence**: `executeFlush` at `:10-36` (drops only); `onFlush` at `hook.ts:752-758` (signals sets); drain gate at `transform-postprocess-phase.ts:1179`.
- **Suggested Fix**: Clarify in the spec that /ctx-flush is NOT required — wrapup publishes ride the next natural materializing pass. If /ctx-flush is suggested, document that it triggers materialization on the NEXT message, not immediately.

## Finding 8: Pi parity — wrapping `runPiHistorian` in a blocking loop is mechanically unsound because Pi's `pi.on("context")` handler is the transform pipeline and the emergency drain awaits ONE historian with a 30s cap, with NO abort surface
- **Severity**: HIGH
- **Location**: `packages/pi-plugin/src/context-handler.ts:1554` (`pi.on("context", async (event, ctx) => {…})` — the transform); `:2056-2113` (emergency drain — `await withTimeout(histPromise, 30_000)` at `:2074`, ONE in-flight historian); `:2818-2926` (`spawnPiHistorianRun` — fire-and-forget, `inFlightHistorian.set` at `:2924`); `:2044-2050` ("We can't `client.session.abort()` mid-pass")
- **Confidence**: high
- **Issue**: The spec claims "Pi parity: same command, same loop, same boundary override, day one" and "the loop wraps runPiHistorian the same way its emergency drain does." Three mechanical problems: (1) Pi's emergency drain (`:2056-2113`) awaits ONE in-flight historian with a 30s cap (`withTimeout(histPromise, 30_000)` at `:2074`) and does NOT loop. A multi-run blocking loop needs a new primitive. (2) Pi's `pi.on("context")` handler (`:1554`) is the per-LLM-call transform — it returns `{ messages }` to replace the array. The handler IS awaited by Pi before the LLM call (the handler is `async` and Pi awaits it — `context-handler.ts:4-6` "Pi fires `pi.on("context", ...)` immediately before each LLM invocation"). So a blocking drain loop inside the context handler IS mechanically possible for the reactive arm. BUT: (3) Pi has NO `session.abort` surface (`:2044-2050` "We can't `client.session.abort()` mid-pass") — the emergency drain cannot abort the in-flight LLM call, it can only await the historian. For the reactive arm (blocking drain before the request goes out), this is fine because the request has NOT gone out yet. For a user-initiated `/ctx-wrapup` command (not on the context handler's critical path), the loop runs off the transform thread, so the 30s cap and no-abort are not directly relevant — but the spec says "the loop wraps runPiHistorian the same way its emergency drain does," and the emergency drain's 30s cap is per-await, not per-loop. A multi-run loop with a 30s-per-run cap on a 280k gap would time out after the first run and proceed with the un-compacted prompt → the exact 400. (4) `spawnPiHistorianRun` (`:2818`) is fire-and-forget (`inFlightHistorian.set` at `:2924`, not awaited). Wrapping it in a blocking loop requires awaiting `runPromise` directly, which the current code does not do (it's stored in `inFlightHistorian` for the emergency drain to await). The reactive arm would need to await `runPromise` in a loop with re-spawns.
- **Evidence**: Emergency drain single-await at `:2074`; no abort at `:2044-2050`; `spawnPiHistorianRun` fire-and-forget at `:2924`; `pi.on("context")` is async and awaited (`:1554`, `:4-6`).
- **Suggested Fix**: Build a dedicated Pi blocking drain-loop primitive that (a) spawns `runPiHistorian` via `spawnPiHistorianRun`, (b) awaits `inFlightHistorian.get(sessionId)` with a PER-LOOP deadline (not 30s — needs a multi-run total budget), (c) re-resolves boundary + re-spawns each iteration. Do NOT reuse the emergency drain's 30s single-await. For the reactive arm, the loop runs inside `pi.on("context")` (awaited by Pi) — verify Pi's handler timeout (if any) accommodates minutes-long blocking.

## Finding 9: `recordProtectedTailPublicationFloor` resets `recovery_no_eligible_head_count=0` per publish — wrapup's many publishes reset this counter repeatedly, which is benign for wrapup but could mask a genuine no-eligible-head escape that armed mid-wrapup
- **Severity**: LOW
- **Location**: `packages/plugin/src/features/magic-context/storage-meta-persisted.ts:341-355` (`recordProtectedTailPublicationFloor` — `recovery_no_eligible_head_count = 0`); `transform.ts:750-753` (`noHeadEscape` uses `recoveryNoEligibleHeadCount >= RECOVERY_NO_HEAD_LIMIT`); `protected-tail-boundary.ts:145` (`RECOVERY_NO_HEAD_LIMIT = 2`)
- **Confidence**: medium
- **Issue**: Each wrapup publish calls `recordProtectedTailPublicationFloor` (`compartment-runner-incremental.ts:668`), which resets `recovery_no_eligible_head_count=0` (`storage-meta-persisted.ts:351`). This is correct for a successful publish (the head was eligible). But if a concurrent transform pass armed `needsEmergencyRecovery` mid-wrapup (e.g., a different pressure spike) and the no-eligible-head count was climbing toward `RECOVERY_NO_HEAD_LIMIT=2` to trigger the escape notification (`transform.ts:767-774`), each wrapup publish would reset the counter to 0, preventing the escape from ever firing. This is a narrow race (wrapup publishes are fast relative to transform passes) and the escape is a UX notification, not a correctness mechanism. The `noHeadEscape` only suppresses the percentage bump and sends an ignored message — it does not affect wrapup. Low severity.
- **Evidence**: `recordProtectedTailPublicationFloor` resets counter at `:351`; `noHeadEscape` threshold at `transform.ts:752`; `RECOVERY_NO_HEAD_LIMIT=2` at `protected-tail-boundary.ts:145`.
- **Suggested Fix**: Acceptable. Document that wrapup publishes reset the no-eligible-head counter (correct behavior — each publish proves the head was eligible).

## Summary

**Findings by severity**: 1 BLOCKER (F1), 2 HIGH (F2, F5, F8 — three HIGH), 2 MEDIUM (F3, F7), 2 LOW (F4, F9). F4 and F9 are effectively non-issues with evidence.

**Overall verdict: REVISE** (leaning BLOCK on phase-2 reactive arm alone)

The spec's v1 user-initiated `/ctx-wrapup` command is mechanically realizable with caveats: the runner needs a new `forceKeepLastCompartment` dep with a decision on promotion (F2), a wrapup-level cross-process guard + whole-loop lease (F5), and a dedicated meaningful-message counter for the no-op guard (F6). The deferred marker blob clobbering is benign (F3). The /ctx-flush UX needs clarification (F7).

The phase-2 reactive arm is the BLOCKER (F1): the existing blocking surface (`awaitCompartmentRun`) awaits ONE run with a single 120s timeout and does NOT loop. A 280k-token downswitch gap needs many sequential runs. There is no loop primitive, no total budget, and no mechanism to re-resolve + re-start while still blocking `messages.transform`. Building this is a substantial new surface, not a reuse of the emergency drain. Pi parity (F8) compounds this: Pi's 30s single-await emergency drain and fire-and-forget `spawnPiHistorianRun` likewise cannot loop without a new primitive, and Pi's no-abort surface limits recovery options.

**The 1-3 findings driving the verdict**: F1 (reactive arm not mechanically realizable with current await surface), F2 (discard-last OFF has no mechanism and promotes weak-boundary durable state), F5 (wrapup-vs-wrapup/wrapup-vs-recomp needs a cross-process guard + whole-loop lease). Ship v1 (user-initiated, non-blocking) after F2/F5/F6 are addressed; BLOCK phase-2 reactive arm until F1/F8 are designed with a real loop primitive + total budget.
