## H2 (HIGH, cache-correctness race): m0 memory load happens before the watermark read
m0 composition loads memory rows first (m0_compose.rs:126-141), then reads max_memory_id / memory_mutation_cursor SEPARATELY; commit CAS checks only mc_cache_state.row_version (mc-store/src/lib.rs:2188-2213), not the memory source revision. Interleaving: compose loads OLD rows → a write commits → compose reads NEW watermarks → renders old bytes but stores advanced watermarks → next SOFT filters by the already-advanced cursor and emits no correction → stale/missing memory until the next HARD.
FIX: load the m0 memory rows AND their watermarks (max_memory_id, mutation_cursor) from ONE consistent SQLite snapshot (single read transaction), and recheck that memory source revision inside the cache commit CAS (extend the fence to cover a memory-revision token, reusing the existing CAS retry loop on mismatch). The rendered bytes and the stored watermark must come from the same snapshot. Test: interleave a memory write between compose-load and commit (failpoint/hook) → assert either the pass renders new bytes OR the CAS rejects and retries; never renders-old-but-advances-watermark.

## H3 (HIGH, atomicity): public-op validation outside the transaction + partial batch archive

Make batch archive all-or-nothing in one immediate transaction. Require merge target/source disjointness. Handle the normalized-content duplicate case (see M5). Tests: concurrent-merge (both preflight active → second rejected/consistent lineage), partial-batch-archive (one bad id → whole batch rolls back).
