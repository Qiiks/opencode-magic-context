## Fix 1 (HIGH): dirty_floor_ordinal can clear before its gap is covered → permanently missing FTS rows
message-index-async.ts reconcileSessionIndex snapshots the message source (readMessages) BEFORE taking the context-DB writer lock (~:137-151). message-index.ts getUpsertCleanIndexStatement writes dirty_floor_ordinal = 0 UNCONDITIONALLY (~:64-69) and indexMessagesAfterOrdinal advances the watermark to the snapshot end (~:301-333). Interleaving: reconcile snapshots messages ending at k-1; another process records dirty floor k; reconcile writes dirty_floor=0 without having message k; a later live success at k+1 advances the watermark past k → message k is NEVER indexed and the omission survives restart. Also: a failed incremental live write records the floor only afterward in an unguarded catch (message-index-async.ts:192-217) — if markMessageIndexDirty itself hits contention or the process crashes between failure and marking, the floor stays unset AND the local reconciliation latch isn't cleared.
FIX: (a) make watermark advancement CONTIGUOUS — never advance the last_indexed_ordinal past a gap; if the source snapshot doesn't cover an ordinal ≤ the intended watermark, retain (watermark_min = that ordinal) as the dirty floor instead of clearing to 0. (b) Clear the dirty floor ONLY when the current snapshot demonstrably covers it: if finalWatermark < dirtyFloor, PRESERVE the floor (don't write 0). Don't delete/reindex rows beyond the snapshot. (c) The failed-live-write path: set the floor BEFORE (or atomically with) the risky write, or ensure the reconciliation latch is cleared if marking throws so a retry re-attempts. (d) Guard the mark: if markMessageIndexDirty throws, the next reconcile must still cover the gap (don't leave both the floor unset AND the latch set). Tests (two-connection / injected): stale reconciliation snapshot ending before a recorded floor → floor preserved, gap indexed next pass; failed dirty-mark → gap still covered; out-of-order live events → no ordinal lost; crash between failure and mark → recovered.

## Fix 2 (HIGH): the "async" FTS reconciler + session-project backfill do unbounded synchronous event-loop work
message-index-async.ts defer() just moves to another macrotask (~:80-88); the task synchronously loads+parses every message and part (read-session-raw.ts:83-124) then iterates the whole array while holding BEGIN IMMEDIATE (message-index.ts:301-333); clear-and-reindex same (~:223-243). Scheduled from BOTH transform (transform.ts:466-468) and event handling (hook-handlers.ts:330-332). No batch/time-budget/yield. Separately, session-project-backfill.ts: index.ts:182-209 synchronously selects EVERY OpenCode session before the runner; the runner processes synchronously until ten NEW DIRECTORIES not ten sessions (:148-197,199-268) — thousands of sessions sharing one dir never yield — and each uncached identity does synchronous git rev-list with a 5s timeout (project-identity.ts:25,262-287): up to 10 blocking git calls before the first real await.
FIX: (a) FTS reconciler: page the source read + indexing into bounded batches (e.g. N messages per transaction), yielding (await) between transactions instead of one full-session BEGIN IMMEDIATE. Keep correctness (contiguous watermark from Fix 1). Cap per-tick work with a time or row budget; resume next tick. (b) Backfill: page session discovery (don't SELECT all sessions up front — batch), yield by ELAPSED TIME or PROCESSED ROWS (every N sessions, not N new directories), and renew the lease across yields so a slow environment doesn't lose it. Make identity resolution async or yield around the blocking git calls so at most a small bounded number run before an await. Verify the async yield loop ACTUALLY yields (awaits a real microtask/timer, not just a sync loop). Tests: a session set larger than the batch yields (assert the loop awaits between batches — e.g. via an injected clock/counter); backfill with many same-directory sessions yields; lease renews across a long run.
