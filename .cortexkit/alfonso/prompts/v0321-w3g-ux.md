# W3-G — TUI/RPC UX batch (v0.32.1), 9 findings

Repo ~/Work/Projects/CortexKit/magic-context, branch subc-migration, packages/plugin/src/. These are the medium/low findings from the TUI/RPC audit; the 1 High (notification protocol v2) already merged. Verify each at source. All are in shared/rpc-*.ts, tui/*, plugin/rpc-handlers.ts — do NOT touch transform/cache code. Where a fix has a tui/ source, mirror it into tui-compiled/ (the precompiled sidebar) and keep the compiled-freshness gate green.

#3 (MED) — port discovery has no instance affinity + retries only one candidate (shared/rpc-client.ts:114-165,177-182): discovery picks the record with the largest started_at regardless of PID; a stale-newest-but-alive PID blocks discovery of an older healthy endpoint; a 2xx from an unrelated service is accepted. FIX: prefer records whose PID matches process.pid, iterate ALL ordered candidates until one validates, verify the /health body against the record's PID + instance_id, and reset+rediscover on 401.

#4 (MED) — sessionless TUI treated as connected to every session (shared/rpc-notifications.ts:51-60,206-211; tui/data/notification-socket.ts:193-197; tui/index.tsx:758-775): a home-screen (session-less) modern socket matches every scoped notification → scoped toasts/dialogs fire + get acked outside their session, suppressing the persistent fallback. FIX: for modern (protocol-2) sockets a missing session matches ONLY global notifications and must NOT satisfy isTuiConnected(sessionId).

#5 (MED) — fast sidebar poll paints one session's state into another (tui/slots/sidebar-content.tsx:505-528,549-609,638-643): recompTick() is not guarded by captured session id; switching sessions mid-fetch lets session A's response overwrite B. FIX: key polling state to a captured session id, cancel/reset on session-change, reject stale-session/stale-sequence responses.

#6 (MED) — RPC failures shown as success (tui/data/context-db.ts:252-284; tui/index.tsx:392-413,469-487): getCompartmentCount() turns errors into a real-looking 0; recomp/upgrade confirmation shows "requested"/"started" WITHOUT awaiting the request result. FIX: preserve an explicit error result; await requestRecomp()/upgrade before showing success; show a failure toast on false.

#7 (MED) — disabled/conflicted install reintroduces idle discovery work (tui/index.tsx:726-730,821-835; rpc-client.ts:11-14,37-43,129-143; notification-socket.ts:103-128): when the server is intentionally absent, startup awaits ~13.5s nested discovery retries THEN checks conflicts, and starts the reconnecting socket before the conflict gate. FIX: run the local conflict gate BEFORE awaiting RPC / starting the socket; make WS endpoint resolution single-attempt and let its own backoff own retries.

#8 (MED) — sticky sidebar cache can never serve on failure (tui/data/context-db.ts:122-133,142-172): line ~129 tests in-flight evidence on the EMPTY fallback instead of the cached snapshot, so the condition is always false → deletes cache + returns zeros on any transient failure. FIX: evaluate the CACHED snapshot; return any unexpired cached snapshot on transport/error-envelope failures; keep trusting a successful zero-valued server response (so deleted sessions aren't resurrected).

#9 (LOW) — dispose/reinit resource ownership (notification-socket.ts:70-101,114-140; sidebar-content.tsx:55-75): startNotificationSocket() has no connecting-guard/stale-attempt check → overlapping init can create multiple sockets; stopNotificationSocket() retains opts+cursor; sidebar discards the preference-watcher disposer. FIX: track one in-flight connection attempt + close losers of the generation race; on dispose clear opts+epoch state, retain the preference-watcher disposer and invoke it from api.lifecycle.onDispose().

#10 (LOW) — notification queue cap is not a cap (shared/rpc-notifications.ts:86-106): eviction keeps the newest per distinct session, so >100 sessions each with one unacked notification grows unbounded + re-sorts the whole queue per push. FIX: impose a real global bound with a bounded per-session reserve or age-based expiry.

#11 (LOW) — bearer token in the WS URL (notification-socket.ts:131-135; rpc-server.ts:60-62): the full token appears in the upgrade query string (capturable via diagnostics/proxy logs). FIX: use Bun's WebSocket Authorization-header support if available, or a short-lived one-time upgrade nonce; keep hello-auth as defense in depth. If header support isn't cleanly reachable, do the nonce; if neither is feasible without larger surgery, document why and defer THIS one only (note in report).
