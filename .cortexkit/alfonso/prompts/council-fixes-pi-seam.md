# Fix Pi materialization/marker-seam findings from release council (branch subc-migration)

Four verified findings in the Pi deferred-materialization / compaction-marker seam plus one OpenCode rehydration mirror. Read the current code first. This is cache-critical work: every change must preserve "defer passes replay byte-identical" and "one bust covers both the history rebuild and the marker advance".

## P1 (P0-class): Pi must not advance the compaction marker past history the pass did not render
packages/pi-plugin/src/context-handler.ts: the deferred-history drain (~4369-4400) gates on materializationSatisfiedThisPass, which is set true right after applyPendingOperations succeeds (~3775) — it says nothing about what injectM0M1Pi actually rendered. Under PiMaterializeContentionError, injection falls back to replayCachedM1Pi (inject-compartments-pi.ts ~2110), which serves the cached m0/m1 WITHOUT validating coverage against current compartments (unlike softRefreshCachedM1Pi, it never checks cachedPiRowMatchesSnapshot). historyWasConsumedThisPass still goes true (~4316), so the drain calls appendCompaction and advances Pi's native marker past compartments that are NOT in the rendered m1, then consumes the deferred signal — the wrapped/published history disappears from the wire until an unrelated bust. OpenCode is protected by pendingMarkerCoveredByConsumedBoundary in transform-postprocess-phase.ts; Pi needs the equivalent.
Fix: thread the injection outcome into the drain decision. injectM0M1Pi already returns m0Materialized and internally knows contentionExhausted and the boundary it trimmed to (findCompartmentBoundaryForSnapshot(markers) → boundaryId). Extend the injection result with what the drain needs (e.g. contentionExhausted: boolean and renderedBoundary info), then gate deferredHistoryDrainEligible so the marker apply happens ONLY when the pending marker's target is covered by the boundary this pass actually rendered (endMessageId match or ordinal <=), mirroring OpenCode's pendingMarkerCoveredByConsumedBoundary semantics. On contention fallback: suppress the drain AND preserve both deferred signals so the next successful pass drains. Keep the existing casLost / suppress paths intact.
Tests (non-vacuous): (a) contention-fallback pass with a pending marker → appendCompaction NOT called, pending blob + deferred signals survive; (b) subsequent successful materialize pass → marker applied once and signals consumed; (c) normal non-contention publish → unchanged behavior. Use the existing context-handler test harness patterns; simulate contention via the injection seam if one exists, else add a minimal test hook rather than racing real processes.

## P2: restart rehydration must use the gated deferred signals (both harnesses, symmetric)
Pi: packages/pi-plugin/src/index.ts (~533-537) rehydrates pending-marker sessions with signalPiDeferredHistoryRefresh + signalPiPendingMaterialization. The pending-materialization signal feeds baseShouldApplyPendingOps directly (context-handler.ts ~3720-3724), an explicit-flush-strength forced materialization — a restart remnant of a background/manual publish must NOT force a bust; it should ride the next natural one. Switch to signalPiDeferredMaterialization (the canConsumeDeferredLate-gated path the live wrapup/publish path uses).
OpenCode: packages/plugin/src/hooks/magic-context/hook.ts (~250-262) rehydrates only deferredHistoryRefreshSessions from getSessionsWithPendingMarker; the live publish path (wrapup-orchestrator.ts onCompartmentStatePublished) sets BOTH deferredHistoryRefreshSessions and deferredMaterializationSessions. Add the sessions to deferredMaterializationSessions in the rehydration loop too, so a crashed/restarted publish resumes with the same signals it had live.
Tests: Pi — after rehydration, a defer pass does NOT apply pending ops (no explicit_flush), and the next natural bust drains the marker; OpenCode — rehydration seeds both sets.

## P3: Pi auto-search must not persist retryable failures
packages/pi-plugin/src/auto-search-pi.ts (~312-320 replay+exit, ~402-416 persists error/timeout): a transient timeout/error is persisted as a permanent no-hint decision, suppressing auto-search for the rest of the turn. OpenCode persists only stable outcomes and leaves timeout/error retryable (auto-search-runner.ts ~349-365, test at auto-search-runner.test.ts ~170-181). Match OpenCode: persist empty/below-threshold/too-short/stacked; do not persist error/timeout. Port the OpenCode retry test.
