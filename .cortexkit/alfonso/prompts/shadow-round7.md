CONTEXT. The shadow lane mirrors OpenCode transform passes into the Rust module and byte-compares outputs (dev flag shadow_transform.enabled). After today's four-class fix the lane runs cleanly and post-restart divergences dropped to exactly the classes below, verified from live store reads (shadow_divergences table in ~/.local/share/cortexkit/magic-context/store.db; everything before created_at 2026-07-16T17:14Z predates the fixes and is noise).

FIX 1 (the dominant real divergence): USER-PROFILE NEVER SYNCS. TS m0 renders a <user-profile> block between </project-docs> and <session-history> (from active user memories). The Rust m0 composer reads store.load_active_user_memories() (crates/mc-module/src/m0_compose.rs:153) from the module's OWN mc_user_memories table, which is empty for shadow sessions: the sender's state_sync seeds compartments, memories, memory_mutations, and marker state, but never user-profile lines. Result: byte-mismatch at exactly the <user-profile> boundary on every m0-rendering pass (321 of the 688 pre-fix byte rows, and 1 of the 2 post-fix rows). Fix: (a) sender includes the active user-profile lines (ordered, verbatim strings, same source the TS renderer uses: getActiveUserMemories ordering promoted_at ASC, id ASC) in the cold-start seed payload; (b) module persists them shadow-scoped (a shadow_user_profile table in mc-store keyed by the shadow project path, or rows in the existing shadow-scoped stores if one fits; NOT the global mc_user_memories, which the owned leg owns); (c) m0_compose reads the shadow-scoped profile when composing for a shadow session (the shadow project path already discriminates; keep the owned-leg path untouched); (d) profile changes mid-session do not need live deltas in v1: the next divergence will flag once and the reseed carries the new profile, but add a comment saying exactly that so nobody mistakes it for an oversight. Regression test: seed with profile lines, compose m0, assert the <user-profile> block bytes match the TS renderer's fixture for the same lines (there are existing differential goldens for memory_render; extend that pattern).

FIX 2: SINGLE ITEM OVER THE 512KiB PAGE LIMIT. Session ses_331acff9 (the largest live session) cannot mirror: "shadow: send failed (ignored): shadow transform item exceeds the 512 KiB page limit" repeating every pass. The transform paging added today pages at ITEM granularity, so one message larger than one page is unsendable. Fix: allow a single oversized item to span multiple pages (content-slicing with an item-continuation marker inside the page payload, digest per page as today; module reassembles the sliced item before reassembling the array). Keep the aggregate caps. If you find a cleaner boundary (e.g. slicing the serialized JSON of the whole array rather than item-array chunks) you may restructure, but the reassembled request must stay byte-equivalent and the interleave guard must hold. Regression test: one 2MB synthetic item pages, reassembles byte-identical, and a mid-flight generation change discards cleanly.
