## Fix 1 (HIGH): migration conflict handled too late → losing process wedges on concurrent startup
runMigrations() (migrations.ts:~1974-1994) computes pending migrations, then enters a DEFERRED db.transaction() (shared/sqlite.ts:137-157). Several migrations incl v50 READ schema state before their first write (migrations.ts:1881-1886). Two processes both take read snapshots; after one commits, the other gets SQLITE_BUSY/SQLITE_BUSY_SNAPSHOT on the writer upgrade — BEFORE the schema_migrations PK-conflict path, so isSiblingMigrationConflict() (storage-db.ts:1578-1585) can't recover it and openDatabase fails closed. OpenCode Desktop loads one instance per project in one process + TUI + subagents → real concurrent-startup wedge.
FIX: acquire BEGIN IMMEDIATE at the start of the migration application, then RE-READ the persisted schema version UNDER THAT LOCK before choosing/applying the next migration (so only one process applies; the other reads the already-advanced version and skips). Keep the existing PK-conflict tolerance as a secondary belt. The per-migration body + its version insert must stay in ONE transaction (already true — preserve it). Do NOT hold the immediate lock across ALL migrations if that risks a long hold on a big upgrade — acquire-immediate / re-read / apply-one / commit / loop is the safe shape (each iteration re-checks under the lock). Test (the existing migrations-race.test.ts misses this — its cases pre-clear the version row so nothing is pending): a deterministic TWO-CONNECTION test with a GENUINELY PENDING migration (pre-v51 DB, both connections call runMigrations) → both succeed (one applies, one skips via the under-lock re-read), neither throws SQLITE_BUSY out of openDatabase, final schema is correct and applied exactly once.

## Fix 2 (MEDIUM): clearSession orphans tool_owner_backfill_state
tool_owner_backfill_state is created OUTSIDE the versioned schema (tool-owner-backfill.ts:98-110, ensureBackfillStateTable) and is session_id-keyed. clearSession() (storage-meta-session.ts:165-192) never deletes it → orphan row per deleted session. (session_project_backfill_state is harness-keyed, NOT affected — leave it.)
FIX: (a) create tool_owner_backfill_state in the VERSIONED schema via v51 (move it into the migration + fresh-DB schema in storage-db.ts) so it's a first-class session table, keep the ensureBackfillStateTable CREATE IF NOT EXISTS as the idempotent backstop; (b) add `DELETE FROM tool_owner_backfill_state WHERE session_id = ?` to clearSession; (c) prevent the backfill from RECREATING the row for a session with no tags left (guard: don't insert a backfill-state row if the session has zero tags). Test: clearSession removes the backfill-state row.

## Fix 3 (MEDIUM): v5 healer swallows non-schema errors then records complete
The healing helpers (storage-schema-helpers.ts:67-76,105-114,151-159) catch EVERY UPDATE error though the comment says "tolerate only missing columns." Migration v5 (migrations.ts:250-270) invokes the healer then records v5 complete; it's intentionally NOT rerun at startup (storage-db.ts:1401-1407). A transient SQLITE_BUSY / non-schema error skips part of the heal silently; if a later statement succeeds, v5 commits complete and the skipped repair is permanent. (The backfills use WHERE col IS NULL so concurrent writes aren't clobbered — that part is clean.)
FIX: make the healers skip only GENUINELY ABSENT columns (inspect schema via PRAGMA table_info before the UPDATE, or match specifically on the "no such column" error text/code) and RETHROW all other errors so the migration runner rolls back and retries. Because already-recorded v5 rows won't rerun, add a v51 REPAIR step that re-runs the heal idempotently for DBs that recorded v5 under the old swallowing behavior. Test: a healer given a non-schema error rethrows (migration not recorded complete); a missing-column case still tolerated.

## Fix 4 (MEDIUM): deferred read-then-write transactions → SQLITE_BUSY on lock upgrade
These use db.transaction() (deferred) and read before their first write, so the writer-lock upgrade can bypass busy_timeout and throw SQLITE_BUSY under concurrent writers:
- review-user-memories.ts:274-308 (lease validation then commit) — use the existing runLeaseGuardedWrite helper (memory #8411).
- plugin-messages.ts:138-153 (consume/select then mark consumed)
- storage-tags.ts:1334-1373 (tag lookup then delete)
- v22-deferred-backfill.ts:281-368 (collision lookup then mutate)
- tool-owner-backfill.ts:394-467 (lookup then update)
FIX: convert each to BEGIN IMMEDIATE (the shared sqlite transaction helper supports it; or runLeaseGuardedWrite where lease-shaped). These are availability fixes (SQLite rolls back, no data loss) but they cause avoidable pass failures. Keep behavior identical otherwise. No new test required beyond existing coverage staying green, but add one if a path lacks any.
