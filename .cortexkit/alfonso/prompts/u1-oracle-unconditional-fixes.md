## F1 — fold TAGGER_FEATURE_EPOCH into effective render identity (epoch law violation, fix is LIVE-path)
lib.rs:143-152 declares TAGGER_FEATURE_EPOCH but deliberately omits it from module-side folding; transform.rs:801-814 effective_render_config folds only profile_render_epoch; tagging_active reads the raw gate (transform.rs:671-678). Consequence: a future MC-first deploy stagger could start tagging an established session with NO coordinated HARD — violating the self-fold-covers-content law (every byte-affecting epoch component folds module-side, omitted-at-zero).
FIX: fold the tagger epoch into effective_render_config via the SAME omitted-at-zero M0ContentEpoch pattern as mpe/mre (component tag e.g. "tfe{n}", omitted at 0 so existing render_config strings stay byte-identical today). AND derive tagging activation from the folded epoch value, not the raw gate — i.e. tags may only render when the epoch component that forced the HARD is present in the committed render identity, so activation is self-coordinating by construction (a session still on the pre-flip identity NEVER gains tags mid-session). Add the test: flip the gate mid-session (test seam) → pass takes exactly one HARD with the new identity, and the pass BEFORE the HARD emits zero tags.

## F2 — [dropped §N§] placeholder for reduced-but-tagged targets
selection.rs:297-302 freezes numberless "[dropped]" replacement bytes. The canonical TS behavior (packages/plugin/src/hooks/magic-context/apply-operations.ts:41-53) is "[dropped §N§]" — a pure function of the tag id — so the model can correlate a dropped block with the number it referenced. On the anthropic-family profiles the placeholder must carry the tag reference when the target HAS a tag row; targets with no tag row keep plain "[dropped]".
FIX in the selection/replacement path: when freezing a drop replacement for a target that has an mc_tags row for that session, freeze "[dropped §N§]" (N = tag_number). Frozen units are immutable-once-frozen: this changes NEW freezes only — no migration of existing frozen units (they replay as-is; changing them would bust caches). Tests: tagged target → placeholder carries its number; untagged target → plain; already-frozen unit unchanged by the new code path.

## F4 — byte-idempotent overlay strip
transform.rs:2475-2498 strip_tag_prefix uses trim_start(): original "  x" renders "§N§   x"? — no: the bug is the INVERSE direction: text "  x" tagged renders "§N§   x" and after strip becomes " x" (whitespace loss), and attacker-supplied leading "§M§ " in genuine content gets deleted. The strip must be an EXACT inverse of the prepend: strip exactly the prefix bytes the overlay adds ("§{N}§ " with the known N for that block from mc_tags) and nothing else — never pattern-strip arbitrary §-syntax, never trim whitespace.
FIX: make the overlay prepend and its strip a matched pair: prepend adds EXACTLY "§{N}§ "; strip removes EXACTLY that known-N prefix when present, byte-preserving everything else (including user content that literally starts with "§7§ " — only the block's OWN registered number is a candidate, and only one occurrence). Property test: for arbitrary content strings (leading whitespace, forged § prefixes, unicode), strip(prepend(x)) == x byte-exact, and strip(x) == x when x doesn't carry the block's own registered prefix.
