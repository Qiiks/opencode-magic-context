## Fix 1 (Medium): OpenCode discovery probe has two deterministic false-negative modes
db.rs load_recent_opencode_cache_sessions (~:1732-1800): considers only the newest `limit*4` sessions (200 for limit 50), and retains a candidate only if a qualifying assistant cache event exists among its newest 200 message rows. So: (a) a session whose last cache event is older than its newest 200 raw rows (heavy tool-use turns each create message rows) disappears; (b) if 200 newer unarchived candidates all fail the probe, an older event-bearing candidate is never examined.
FIX: page the candidate scan until `limit` qualifying sessions are found (or a sane hard ceiling — e.g. scan in batches of limit*4 ordered by time_updated DESC, keep going until enough qualify or a max-scanned bound like 2000 sessions is hit), instead of a single limit*4 slice. For the newest-200-rows probe: the probe exists to avoid scanning full history — keep it index-friendly, but make the event-existence check authoritative for the session rather than window-limited. Options (pick one, justify + measure): (i) the FIRST_OPENCODE_CACHE_EVENT_SQL index probe (ORDER BY time_created ASC LIMIT 1 with the json predicate) already exists elsewhere in this file for first-event detection — a session HAS a cache event iff that probe returns a row; use that per-candidate existence probe (one indexed seek per candidate, cheap) instead of scanning its newest 200 rows; (ii) keep the newest-200 probe but only as a fast-path, falling back to the authoritative probe when it misses. Prefer (i) if the per-candidate cost stays low at scale (measure with the profiler at the real DB size). Preserve the archived-session exclusion (time_archived IS NULL).

## Fix 2 (Medium): UI harness/subagent filters run AFTER the global 50-session cap
db.rs applies managed/unmanaged filtering server-side BEFORE truncation (~:2006-2013, correct), but CacheDiagnostics.tsx applies harness and subagent filters only AFTER receiving the capped 50 (~:155-169, 342-350). So 50 newer other-harness sessions make a selected-harness view look empty; 50 newer subagents leave the default hide-subagents view empty though older primaries exist.
FIX: the cheapest correct fix is to raise the backend candidate/return budget so the frontend filters have enough to work with, OR pass the harness/subagent intent to the backend so the cap applies AFTER those filters. Since subagent flags and harness are known backend-side (load_cache_subagent_flags, harness on each row), prefer: apply the subagent filter server-side before the cap when the frontend requests hideSubagents (thread the two booleans the frontend already has — showUnmanaged is already threaded; add hideSubagents and an optional harness filter), so the returned 50 are 50 the user will actually see. Keep showUnmanaged semantics unchanged. Frontend then filters only as a cheap redundant guard. Verify the tick path (reconcile) uses the same filtered call so it doesn't churn.

## Fix 3 (Medium): eventless Pi sessions become zero-stat cards and displace eventful ones
pi_sessions.rs scan returns EVERY valid Pi session file without requiring an assistant usage event; db.rs treats all Pi sessions as managed (~:217-219) and appends them (~:1978-1982), sorted by activity. The frontend full-loads an empty window and emits a `0 events / 0%` card, occupying a recent slot ahead of older event-bearing sessions.
FIX: exclude eventless sessions from the cache list at the source — a Pi session qualifies for the CACHE page only if it has ≥1 assistant message with usage.total > 0 (mirror what the external CC/Codex scanners already do — the audit notes they reject eventless files). Either filter in the Pi meta scan used by the cache list (add a has-cache-event check to the meta, cheaply — Pi meta already reads the file; compute a has_usage_event flag during the existing parse, don't add a second read), or filter in db.rs before appending. Do NOT break other Pi consumers of scan_pi_session_dir (SessionViewer etc.) — if they need eventless sessions, add a cache-specific filtered variant rather than changing the shared scan. Keep the mtime-cache fast path intact.
