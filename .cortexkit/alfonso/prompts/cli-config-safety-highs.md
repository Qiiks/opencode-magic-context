# Fix: two CLI data-safety Highs (config-overwrite + schema-fence bypass)

Repo ~/Work/Projects/CortexKit/magic-context, branch subc-migration, packages/cli/src/. Two verified audit Highs. Verify each at source first. Scope is EXACTLY these two — do not touch the other CLI findings.

## H1 (HIGH): setup treats a parse FAILURE as empty config and overwrites it
Sites: commands/setup-pi.ts:118-119 and :146-147 (`readJsonc(path) ?? {}`), and any sibling in setup-opencode.ts with the same `readJsonc(...) ?? {}` shape. Also lib/prompts.ts:81-85 (Ctrl-C/exit behavior).
Bug: `readJsonc(existing) ?? {}` collapses BOTH "file missing" (→ {} is correct) AND "file exists but is unparseable" (→ {} is DESTRUCTIVE — a single malformed brace in the user's real settings.json / magic-context.jsonc becomes {} and gets written back, erasing their config). Same class as the June config-eating migrator bug.
FIX: distinguish the three cases explicitly. readJsonc (or a wrapper) must return a discriminated result: missing (→ start from {}), parsed-ok (→ use it), parse-error (→ ABORT the write with a clear error naming the file + the parse location; never default-and-overwrite). Setup must treat parse-error on any existing target as a hard failure that writes NOTHING. If readJsonc currently returns `null` for both missing and unparseable, add existsSync discrimination or a parse-error-throwing variant. Apply to every `readJsonc(...) ?? {}` write-back site in setup-pi.ts and setup-opencode.ts.
Also: prompt cancellation (Ctrl-C) must propagate a cancellation result, not process.exit(0) mid-wizard leaving partial writes — if lib/prompts.ts calls process.exit on cancel, change it to signal cancellation up so the caller writes nothing. (If this is too entangled, fix only the readJsonc-overwrite core and note the cancel path for follow-up.)
Tests: existing-but-malformed settings.json → setup aborts, file UNCHANGED on disk; missing file → setup creates it; valid file → merged correctly.

## H3 (HIGH): CLI DB opens bypass the v51 schema fence
Sites: commands/doctor-opencode.ts:1098 (`new Database(dbPath, { readonly: true })` — no fence), commands/migrate.ts:914-921 and :725-741, commands/migrate-session.ts:509-510. Fence reference: packages/plugin/src/features/magic-context/storage-db.ts (LATEST_SUPPORTED_VERSION=51, the fence-check logic ~:273-308).
Bug: these open the shared context.db directly without checking schema_migrations max vs LATEST_SUPPORTED_VERSION. Against a DB migrated by a NEWER instance (max > 51), doctor reports integrity PASS and migrate paths WRITE to a schema they don't understand → corruption risk. Also migrate.ts can create an empty DB when the data dir exists but context.db does not, then fail on the first compartments query instead of skipping gracefully.
FIX: centralize CLI DB access through one helper that (a) requires the file to already EXIST (never create — no SQLITE_OPEN_CREATE; if missing, skip/degrade gracefully, do not construct a writable handle), and (b) reads schema_migrations max and REJECTS (clear error, no writes) when it exceeds the CLI's supported version. Use a read-only fenced handle for diagnosis; reject unsupported schemas before any migration write. Reuse the plugin's fence constant/logic rather than duplicating the number — import LATEST_SUPPORTED_VERSION if reachable from the CLI, else a single shared source.
Tests: DB at schema max=52 → doctor reports fenced/unsupported (not PASS), migrate refuses to write; DB missing → graceful skip, no empty-DB creation; DB at 51 → normal.
