# Fix 3 wrapup findings from release audit (branch subc-migration)

Three verified findings from a blind release audit of the /ctx-wrapup feature. Read current code first; all paths relative to repo root.

## W1 (HIGH, cache stability): remove Pi wrapup's eager marker drain
packages/pi-plugin/src/commands/ctx-wrapup.ts drains the pending Pi compaction marker per iteration (drainPendingPiMarker at ~385, helper at ~500) via applyDeferredPiCompactionMarker. This mutates Pi's native branch marker OUTSIDE the context pipeline: the next Pi context pass can be a defer pass that replays stale cached m0/m1 bytes while the branch already hides the raw history behind the new marker — the newly wrapped history vanishes from the wire until a later bust. The invariant: one bust must cover BOTH the m0/m1 history rebuild and the marker advance; context-handler.ts already has the correctly gated drain (~4355-4400: applies the pending blob only when historyWasConsumedThisPass && materialization satisfied).
Fix: delete the per-iteration drain call, the drainPendingPiMarker helper, and the drainPendingPiMarkerForWrapup test seam. Each publish already overwrites the pending blob with the newest boundary and signals deferred history/materialization (keep those signals), so the pipeline drains ONCE at the final boundary on the next consuming pass. Update the final success message if it references marker application. Rewrite the test "stops when the pending Pi marker cannot be drained after a chunk": the command must now SUCCEED with the pending blob intact — assert the pending marker state survives the command and both deferred signals are set. Do NOT touch pi-recomp-marker.ts (recomp's eager apply is a separate pre-existing path, out of scope).

## W2 (HIGH): trigger-fired historian must not start while wrapup is active
The isWrapupInProgress guard exists only on the recomp path (compartment-runner.ts executeContextRecompWithResult ~195). Normal trigger-fired historian starts have no guard:
- OpenCode: startCompartmentAgent in packages/plugin/src/hooks/magic-context/compartment-runner.ts — add an isWrapupInProgress(deps.db, deps.sessionId) check at the top; when live, log and return without registering an active run (make sure any caller-side in-flight flag the trigger path sets is cleared — check the call sites in transform/compartment-trigger paths for a compartmentInProgress-style latch and clear it on skip).
- Pi: the trigger path in packages/pi-plugin/src/context-handler.ts that spawns runPiHistorian (search for the spawn site guarded by inFlightHistorian) — add the same isWrapupInProgress skip before registering providers or spawning.
Safety property to preserve: the wrapup marker self-expires (5-min TTL, renewed by the loop), so a crashed wrapup cannot suppress the historian forever — state this in a comment at both guards.
Tests (both harnesses): with a live wrapup marker, the trigger-fired start is a no-op (no producer spawn, no lease taken); with an EXPIRED marker, the trigger fires normally.

## W3 (MEDIUM): Pi zero-progress must not report success
packages/pi-plugin/src/commands/ctx-wrapup.ts: the initial no-op guard checks only rawMessagesAboveLastCompartment <= messagesToKeep, and the loop treats eligibleEndOrdinal <= offset as done — so a tool-arc-fenced/non-runnable boundary can report "Wrapped up 0 messages" as success AND clear emergency recovery. Mirror OpenCode's semantics (wrapup-orchestrator.ts): add the runnable-window check to the initial guard (see hasRunnableCompartmentWindow usage), and on loop exit treat it as complete ONLY when lastEnd + 1 >= targetEligibleEndOrdinal; otherwise report partial (no recovery clear, "Run /ctx-wrapup again" guidance). Test: a fenced non-runnable boundary with raw count > keep returns a non-success message and leaves emergency recovery armed.
