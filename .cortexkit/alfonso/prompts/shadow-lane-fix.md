# Shadow transform lane: fix the four live-soak failure classes

Repo: ~/Work/Projects/CortexKit/magic-context, branch subc-migration. Spans BOTH the TS sender (packages/plugin/src/hooks/magic-context/shadow-sender.ts) and the Rust module (crates/mc-module). Gates: `cd packages/plugin && bun test` AND `cargo test -p mc-module --lib` AND `cargo clippy -p mc-module`. Comments explain WHY, no plan references, no em-dashes.

CONTEXT. The shadow lane mirrors OpenCode transform passes to the Rust module (dev flag `shadow_transform.enabled`) and byte-compares outputs, so we can prove the Rust transform against real data. A 5-minute live soak today produced 335 resets across 7 sessions at 80-135% CPU, with reset-reason logging now naming four failure classes. Log evidence at /var/folders/18/257zzylx4h1gbkcvs4cnpqqc0000gn/T/opencode/magic-context/magic-context.log (grep "shadow:"). The lane is fail-open: none of this affects the live transform; the cost is CPU and a dead compare lane.

THE FOUR CLASSES (fix all):

F1 OVERSIZE PER-PASS BODIES (hard blocker on exactly the sessions we most want to test). "shadow: send failed (ignored): frame body 88072809 exceeds max 67108864" on a 770-message session, EVERY pass. Cold-start seeds are already paged (sender pages under 512KiB per batch; module reassembles via ShadowSeedCoordinator) but the per-pass shadow_transform request sends the full live array in ONE frame. Fix: page the transform request body with the same coordinator pattern. Sender: when the serialized transform body exceeds the page threshold, split the messages array into ordered pages under 512KiB each (same shape discipline as seed paging: session-scoped, generation-scoped, seq-numbered, digest per page, terminal page carries the rest of the request fields). Module: add transform-page reassembly next to ShadowSeedCoordinator (bounded per-session buffer, aggregate cap; on overflow or generation change discard and answer need_full_resync-style typed error, never panic). The reassembled request must be byte-equivalent to the unpaged form (unit test: serialize a large synthetic request, page, reassemble, deep-equal). While a paged send is in flight, subsequent passes for that session queue or drop-newest (never interleave pages of two passes on one session).

F2 DETERMINISTIC-FAILURE RESET LOOPS (the CPU burner). Every failure path answers reset-and-full-reseed, and a deterministic failure reproduces identically after reseed: sessions cycled to generation 146 (ordinal_mismatch every ~12s) and 68 (quarantine_reseed every ~13s). A reseed is the lane's most expensive operation. Fix in the sender: per-session ring of the last N reset reasons; if the SAME reason fires twice consecutively within a session, PARK the lane for that session for the process lifetime (single log line "shadow: parked (repeated <reason>)", counter, no further sends). A park is not quarantine: no reseed attempts, no timers. Transient classes (transport disconnect, daemon restart detected by connection generation change) are exempt from parking and keep the current retry path. The 30-minute reseed cooldown stays for the non-repeated case.

F3 SEED-BOUNDARY DERIVATION DISAGREEMENT (deterministic mismatch). "seed boundary \"msg_f677011c...#1\" rejected: declared message \"msg_f677011c...\" did not match tail compartment message \"msg_f697b6f6d...\"" looping with reason=shadow_seed_boundary_mismatch. The sender's declared boundary and the module's validation (crates/mc-module/src/lib.rs:5029 area) read from different sources or different orderings. INVESTIGATE both derivations first and report the exact divergence in your notes; then unify: the sender must derive the declared boundary FROM THE EXACT COMPARTMENT SET IT SERIALIZED INTO THE SEED PAGES (max end_message of the serialized rows, same ordering the module uses to pick "tail compartment"), not from a separate DB read that can see a different snapshot. Add a regression test with an out-of-order/mid-publish compartment set proving sender-declared == module-expected.

F4 ORDINAL-MISMATCH CYCLING. One session hit generation 146; the drift check trips identically after every reseed. Suspects (verify, do not guess): provisional ordinals assigned to unpersisted in-flight tail messages (last persisted + n) colliding with the module's durable ordinals after persistence; or the summary-row exclusion asymmetry between readRawSessionMessages-based priming and the id-only ordinal query. Reproduce with a unit test that persists a message AFTER a provisional guess and asserts the memo self-heals WITHOUT tripping reset when the guess was right, and resets ONCE (then succeeds) when it was wrong. If the root cause is the drift check comparing across a generation boundary, scope the memo exactly as the spec pins ({sid, generation}).

Both are inert for the Claude Code leg (shadow ops are OpenCode-leg only and flag-gated), but the report must say so explicitly so the deploy message to the fleet can scope the delta honestly.
