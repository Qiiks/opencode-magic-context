# Fix 6 review findings in the /ctx-wrapup feature (branch subc-migration)

The /ctx-wrapup feature just merged (orchestrators + runner flags + durable marker). An adversarial review found 6 defects; all verified at source. Fix all six with regression tests. Read the current code first: wrapup-orchestrator.ts, compartment-runner-incremental.ts, protected-tail-boundary.ts (resolveWrapupProtectedTailBoundary), transform-postprocess-phase.ts (deferred-marker drain ~1140-1223), compaction-marker-manager.ts, storage-meta-persisted.ts (wrapup marker fns), recomp-orchestrator.ts (runManagedUpgrade), pi-plugin/src/commands/ctx-wrapup.ts, pi-plugin/src/context-handler.ts (deferred history/materialization signaling on publish).

## F1 (HIGH): bind the deferred-marker drain to the boundary this pass consumed
transform-postprocess-phase.ts ~1179: the drain reads the CURRENT pending marker blob and applies it when `historyWasConsumedThisPass` — but the blob may have been overwritten by a publish that happened AFTER this pass's prepareCompartmentInjection (wrapup publishes rapidly while live passes run). Applying a newer blob advances OpenCode's compaction marker past the history bytes this pass rendered into m[0]/m[1]; defer passes until the next bust then replay a frozen injection that does not cover the marker-trimmed raw messages (temporary history omission on the wire).
Fix: before applying, compare the pending blob's target against the compartment boundary this pass actually consumed (the prepare result is available in postprocess — args.pendingCompartmentInjection.compartmentEndMessageId / its ordinal; find the exact field). Apply ONLY when pending.ordinal <= consumed-boundary-ordinal (equal endMessageId also fine). When the blob is NEWER than consumed: do NOT apply, set suppressV12HistoryDrain = true (preserve the deferred signal) so the next consuming pass — whose prepare will have consumed the newer compartments — drains it.
Note the invariant in a comment: one bust must cover BOTH the history rebuild and the marker advance; a marker must never advance past what the pass rendered.
Test: simulate prepare-consumed boundary K, pending blob at K+n (newer) → drain skipped, deferred signal preserved; pending blob at <=K → applied and cleared. Follow the existing postprocess test patterns.

## F2 (HIGH): weak-final behavior must key on the chunk's actual finality, not the plan's
protected-tail-boundary.ts resolveWrapupProtectedTailBoundary sets finalChunk = eligibleEndOrdinal >= targetProtectedTailStart, but readSessionChunk can stop early at historianChunkTokens (chunk.hasMore true). Both orchestrators pass plan.finalChunk into forceKeepLastCompartment, so a mid-loop chunk can (a) persist a weak-lookahead compartment and (b) skip the WHOLE pass's fact/event/observation/primer promotion — and since that range is never re-read, those facts are permanently lost.
Fix: make the runner authoritative. In compartment-runner-incremental.ts (and pi-historian-runner.ts), downgrade the flag internally: effective forceKeepLastCompartment = deps.forceKeepLastCompartment === true && !chunk.hasMore. When downgraded, normal discard-last + promotion behavior applies (the loop will re-read the discarded head next iteration — correct). Keep plan.finalChunk as the orchestrator's HINT but the runner's chunk.hasMore is the gate. Update both orchestrators' comments accordingly (they may keep passing plan.finalChunk or simply always pass true — decide: always pass true from the orchestrators and let !chunk.hasMore be the sole gate is SIMPLER and removes the plan/chunk mismatch class entirely; prefer that, and drop finalChunk from WrapupBoundaryPlan if nothing else uses it).
Test (non-vacuous): a wrapup iteration whose chunk stops early (hasMore) with forceKeepLastCompartment=true → discard-last still applies and facts from the chunk ARE promoted; final iteration (hasMore=false) → compartment kept, promotion skipped. Both harnesses.

## F3: marker ownership loss must abort the loop
wrapup-orchestrator.ts: renewal interval starts AFTER waitForExistingIncrementalRun (which can await a 600s historian run; TTL is 5 min) — the marker can expire and be re-acquired by a second wrapup while the first still runs. And all updateWrapupInProgress null returns (holder mismatch/expired) are ignored.
Fix: (a) start the 60s renewal interval immediately after acquireWrapupInProgress succeeds (before the existing-run await); (b) treat a null return from any updateWrapupInProgress call (including inside the renewal timer) as ownership lost: set a flag the loop checks before starting each iteration; abort with a clear partial message ("another process took over this session's wrapup") without releasing the marker (it's not ours anymore — releaseWrapupInProgress is already holder-guarded, verify and keep the release call, it will no-op).
Pi command: same two changes (its renewal also starts late and ignores nulls).
Test: expire the marker mid-loop (test time hook or direct DB write changing holderId) → loop aborts before the next iteration, does not clear the foreign marker.

## F4: re-fence after user-snap
protected-tail-boundary.ts resolveWrapupProtectedTailBoundary: fenceWrapupBoundaryForToolArcs runs BEFORE snapWrapupBoundaryToUser; the snap moves the boundary to an earlier user message, which can land inside an EARLIER closed arc (queued user messages can interleave mid-arc). Re-run the fence after the snap (loop fence+snap to fixpoint is overkill; fence→snap→fence is enough because the second fence only moves the boundary EARLIER (to the arc's invocation), and an invocation ordinal cannot be inside another arc... verify that claim against buildToolArcs semantics; if it can, iterate to fixpoint with a small bound and a comment).
Test: fixture with user message between a closed arc's invocation and result; keep watermark lands after the arc; snap pulls it inside → final boundary at or before the arc invocation.

## F5: Pi wrapup must signal deferred history/materialization
pi-plugin/src/commands/ctx-wrapup.ts onPublished only updates the status line, then eagerly drains the pending Pi marker per iteration. Normal Pi publish paths signal deferred history refresh + materialization (see context-handler.ts publish handling and ctx-recomp.ts). Without the signal, a successful wrapup leaves Pi's m[1] state stale until an unrelated bust; on drain failure there is no retry signal.
Fix: mirror the normal Pi publish path's signaling on every wrapup publish (find the exact mechanism context-handler uses — deferred sets or DB flags — and invoke the same one). On eager-drain failure, ensure the pending marker + signal survive so the next context pass retries (verify the existing drainPendingPiMarker failure path preserves the blob; the loop already stops with a message — keep that).
Test: Pi wrapup publish → the deferred signal observable by the next context pass is set; drain failure preserves the pending blob.

## F6: guard runManagedUpgrade against wrapup
recomp-orchestrator.ts runManagedUpgrade can take the migration-only path without reaching executeContextRecompWithResult (where the wrapup guard lives). Add an isWrapupInProgress check at the top of runManagedUpgrade returning the same "wait for wrapup" skip message shape the recomp path uses.
Test: upgrade during live wrapup marker → skipped message, no migration ran.
