## intent


GitHub issue #266: users want Magic Context's knowledge layer (project memory, dreamer maintenance, `ctx_search`, notes) WITHOUT MC managing or compacting their context — letting OpenCode's or Pi's native compaction own the window, or letting nothing own it. Ship a user-tier config gate `compaction: { enabled: boolean }` (default `true`). Setting `false` puts the plugin in **compaction-off mode**: the messages transform stays registered and performs additive-only injection (memory/docs via the existing zero-compartment m[0]/m[1] path), raw-message FTS indexing continues, and the dreamer/memory/search stack stays live — while every MC pruning, folding, dropping, splicing, nudging and blocking mechanism is gated off and native compaction is allowed to run.

The full investigation with file+line citations is at `.alfonso/plans/issue-266-compaction-off-report.md` (merged on master; read it FIRST). Where the report's exploratory recommendations differ from the settled decisions below, the settled decisions control (for example, the report's suggestion to unregister `ctx_expand` is superseded by decision 3, and its `compactionOff ⇒ fullFeatureMode=false` shape is superseded by the gate algebra in constraints). Its three load-bearing findings stand: memory reaches the agent ONLY through m[0]/m[1] (so the transform must stay registered, never unregistered); the zero-compartment injection path already implements "memory without history splice" (`inject-compartments.ts:459-472`); and the conflict detector currently treats OpenCode `compaction.auto=true` as a plugin-disabling conflict (`conflict-detector.ts:60-63`, `index.ts:147-155`), so the detector and every setup/fixer/doctor writer must change before or with the mode gate, or compaction-off users get a disabled plugin — the exact inverse of intent.

Settled and binding decisions (from the clarify rounds — do not reopen):
1. Knob is `compaction: { enabled: boolean }` (block convention, matches `memory.enabled`/`todowrite.enabled`, tier-strip machinery operates on paths; `mode: "knowledge-only"` rejected — second mode vocabulary beside `transform_mode` with one non-default value).
2. The mode is named **compaction-off mode** in code and docs.
3. Only `ctx_reduce` unregisters. `ctx_expand` STAYS — it is knowledge-surface, not compaction-surface: its ordinal/range arm reads raw storage (unaffected by markers or mode), it is the dereference half of the ctx_search→ctx_expand loop, and historical-compartment expansion keeps working because we clean markers, not compartment rows. Guidance drops only the tag-based-recovery wording (reuse the existing no-reduce guidance variant machinery; no third vocabulary).
4. Sidebar shows RAW context usage vs the model limit with a mode label ("Context: 41% · native compaction"); MC's execute-threshold fill % must NOT render (a metric may only render if something real acts on it). Historian/compartment-activity rows hidden; memory + notes rows stay; historical compartments may show as a static archived count.
5. Nudges fully off in this mode (Channel 1 AND Channel 2) — closed decision, rationale in constraints; persisted pending Channel-2 intent cleared on the transition pass.
6. The tagger STOPS writing tag rows in this mode (zero new `active` rows, no §N§ prefixes); no retained surface reads active-tag data once drops, nudges, boundary math and sidebar tag counts are all dead. Flip-back self-heals by lazy minting on first observation of untagged wire content. Full reader enumeration in constraints.
7. MC-owned compaction markers are DELETED on the flip-off transition pass (primary mechanism), with inert MC-owned rows as the specified fallback if either mixed-ordering acceptance case contradicts the newest-marker reading of `filterCompacted`.
8. Flip-off on a folded session returns the entire raw history to the wire in one turn; the transition notice and docs state this plainly and MC builds no mitigation (a mitigation would be compaction work in compaction-off mode).
9. Subagent behavior is documentation-only: an OpenCode peer verification of native coverage for child sessions selects between two doc arms; no rescue, reclaim or nudge is built either way.


## constraints


**Config surface**
- `compaction: { enabled: boolean }` in the Zod schema, defaulting at BOTH levels (`z.object({ enabled: z.boolean().default(true) }).default({})` or equivalent): direct parse of `{}`, of `{ compaction: {} }`, and of a config with no block all yield `compaction.enabled === true`; default-on behavior byte-identical to today.
- `isCompactionEnabled(config): boolean` is the ONLY non-schema reader of the `compaction.enabled` config path. Lives beside `config/agent-disable.ts` (precedent: `isDreamerRunnable`/`isHistorianRunnable`); IMPORTED — never re-derived — by `packages/pi-plugin` and `packages/cli`.
- Resolution boundaries (this is what "every gate site calls it" means concretely): the accessor is resolved ONCE at each owning boundary — plugin boot (process-stable tool registration, transform-mode selection, boot advisories), session-hook/transform construction, and each standalone CLI command after it loads user-tier config. Internal transform phases, the sidebar renderer, command handlers and the conflict path receive the resolved boolean (`compactionEnabled` / `compactionOff`); they never receive config merely to re-read the path. The accessor-exclusivity check asserts no other read of the config path, not a call count.
- CLI writers (`setup-opencode`, conflict-fixer, doctor) run outside a session: they load user-tier config through the same loader the plugin uses and resolve it through the same accessor; on load failure they take the preserve-existing-native-fields branch and emit a diagnostic, never assuming either mode.
- The `.describe()` text states: `false` retains memory/dreamer/search/notes/raw-indexing/additive m[0]/m[1]; disables MC context-window management; does NOT enable native compaction; requires process restart (boot-resolved); makes `fail_closed_blocking` inert. CONDITIONAL addition (decision #9): if the OpenCode peer verification finds native compaction does NOT cover subagent/child sessions, the text also gains "subagent sessions have no context management in this mode"; if covered, no addition. SEQUENCING (binding): the peer verification completes BEFORE the schema slice finalizes `.describe()`; if it cannot, the conditional line ships later as a describe-only amendment (text + `build-schema.ts` regen, zero behavior change) rather than blocking the config slice.
- Naming collision is real and must be documented everywhere both appear: MC's `compaction.enabled` (magic-context.jsonc) vs OpenCode's `compaction.auto` / `compaction.prune` (opencode.jsonc) are different files, different owners.
- User-tier ONLY: project-tier `compaction.enabled` is stripped (field-scoped, not block-scoped: a sibling key in a project `compaction` block survives the strip), with a security warning naming the path; identical strip in the Pi loader, for repo-committed and locally-edited project files alike. A cloned repo can never disable the user's context management.

**Conflict matrix and native-field write prohibition (binding, explicit)**
- Call-surface continuity (binding): `detectConflicts` today takes only a directory. It gains the resolved MC config (or an accessor-bearing context) as an explicit parameter, and EVERY production call site — plugin boot, `setup-opencode`, `doctor`, `conflict-fixer` — passes the boot-resolved value. Low-level native-config readers may stay directory-only, but the MC-mode decision is never re-derived at a call site. A repo-wide check asserts no production call site makes a compaction-conflict decision from directory alone.
- With MC compaction ON: existing conflict detection and fix behavior are unchanged, including OpenCode `compaction.auto=true` remaining a plugin-disabling conflict.
- With MC compaction OFF: neither `compaction.auto=true` nor `compaction.prune=true` is a plugin-disabling conflict, and `pluginConfig.enabled` stays `true` through the `index.ts:147-155` block (DCP/OMO conflicts still disable exactly as today).
- Native-field write prohibition: in compaction-off mode `setup-opencode` must NOT write `compaction.auto=false` or `compaction.prune=false` (today it writes both unconditionally, `setup-opencode.ts:84-88`), and `fixConflicts` must NOT flip `compaction.auto` to `false` (`conflict-fixer.ts:161-175`). Pre-existing native values are left byte-for-byte as found. Doctor's auto-fix path (`doctor-opencode.ts:1067-1086`) inherits the same prohibition: it may report, never repair, native compaction fields in this mode.
- DCP and the three OMO conflict classes keep their existing policy in BOTH modes; compaction-off mode does not silently broaden compatibility to third-party message-pruning or recovery hooks. Docs state that the shipped coexistence contract covers OpenCode/Pi native compaction only.
- No-manager configuration (MC off AND native `compaction.auto=false`): boot advisory + doctor report only. MC never enables native compaction and never rewrites a previously MC-written `auto=false`.
- Ordering: conflict-detector, setup, fixer and doctor changes land BEFORE or WITH the mode gate.

**Mode flags and gate algebra (resolves the fullFeatureMode collision)**
- `compactionOff` is a THIRD flag, orthogonal to the existing subagent split `reducedMode = sessionMeta.isSubagent` / `fullFeatureMode = !reducedMode` (`transform.ts:681-682`). It does NOT alias `fullFeatureMode=false`.
- Precedence: every MUTATING gate becomes `existingGate && !compactionOff` — compaction-off wins over both the primary and the subagent path (a subagent session in this mode gets no heuristics, no emergency floor, no drops).
- The m[0]/m[1] injection gate is re-expressed so compaction-off cannot swallow it: injection runs when the memory/docs identity is present AND (`fullFeatureMode || compactionOff`), materialized through the zero-compartment path (`inject-compartments.ts:459-472`). This re-gating is the subject of the memory mutation-direction test.
- Stated consequence (not implicit): a SUBAGENT session in compaction-off mode receives additive memory/docs injection AND no mutating MC gates — i.e. it gains knowledge surfaces it previously lacked and loses MC reclaim entirely. This is tested and documented alongside the subagent doc arm.
- Compartment-history preparation is BYPASSED in compaction-off mode even when historical compartment rows exist: no `<session-history>` render, no raw-tail trim, no boundary splice, no marker write. Memory/docs surfaces are materialized independently of compartment selection.

**Exhaustive additive-only gate list (nothing outside this list changes)**

Staying ON: raw-message FTS reconciliation and event-driven indexing; context-usage measurement and its persistence to `session_meta.last_context_percentage` (the sidebar's only numeric source in this mode); additive m[0]/m[1] memory, docs, user-profile and key-files injection; system-prompt guidance (existing no-reduce variant, tag-recovery wording dropped); session→project binding; dreamer (historian-dependent tasks simply see zero candidates); notes; `ctx_search`, `ctx_expand`, `ctx_memory`, `/ctx-embed`.
Anything not named above stays exactly as it is today; adding a gate requires adding it to this list.
Pi mirror (binding): the list above cites OpenCode files. The slice MUST produce the equivalent enumeration for Pi — `packages/pi-plugin/src/context-handler.ts` (scheduler decision, `heuristic-cleanup-pi`, `injectM0M1Pi`, imports at `:190-194`), `pi-plugin/src/index.ts:1886-1897` (`session_before_compact`), `fail-closed-pi.ts:66-68` — gate each named Pi surface through the same resolved flag, and record the OpenCode→Pi mapping in the slice notes. A gate that exists only on the OpenCode side is an incomplete slice.

**Tool registry and guidance**
- The mode removes exactly the tool IDs produced by `createCtxReduceTools` (`tool-registry.ts:82-86`). That factory is plural: the slice ENUMERATES its emitted IDs by name, and acceptance asserts a tool-set diff equal to that enumeration and nothing else. `createCtxExpandTools`, `createCtxNoteTools`, `createCtxSearchTools` and `createCtxMemoryTools` registration is unchanged (subject to the existing `memory.enabled` gate).
- Guidance uses the EXISTING no-`ctx_reduce` prompt variant with the tag-based-recovery wording dropped: no third variant string, no new template file, no new vocabulary. The rendered section mentions no `ctx_reduce`, no §N§ tags and no tag-recovery workflow, still describes memory/search/notes/`ctx_expand`, and is stable across passes within a process (one system-prompt hash for the mode).

**Notices and advisories (delivery channel, binding)**
- Every user-facing string this mode emits — the flip-off unfold notice, the flip-back `/ctx-wrapup` suggestion, the no-manager boot advisory, the rust-downgrade boot warning, the command refusal line — is delivered OUT OF BAND on the surface that already carries boot warnings and command output. NEVER by writing into the message array, never as a synthetic user/assistant message, never through the Channel-1/Channel-2 nudge machinery (both are gated off; reusing them would reopen closed decision #5).
- Consequence: transform passes stay additive-only at m[0]/m[1] even on transition passes. A transition pass mutates storage and emits an out-of-band notice; its message-array output is indistinguishable from a steady-state compaction-off pass.
- Delivery contract under crash: mutating side effects are exactly-once (idempotent + delete-then-record). Notices are at-least-once — exactly one on a successful uninterrupted pass, with a permitted repeat only in the crash window between emission and mode-record commit. The spec and its tests do not claim crash-proof exactly-once notices unless the notice transport gains a durable dedupe key; if such a key is added it must be specified with the slot in OQ-FIRSTPASS-STORE.
- Boot advisories fire at most once per process. The exact strings live beside the refusal line in ONE source file so docs and tests quote the same constants.

**Tag rows (settled — decision #6)**
- The tagger writes ZERO tag rows in compaction-off mode and emits no §N§ prefixes. Existing rows remain, inert; no tag row drives any behavior; zero rows transition out of `active`.
- Reader enumeration establishing no retained consumer: (a) all drop machinery — gated off; (b) nudge severity math — both channels off; (c) sidebar reclaimable/tag counts — hidden by decision #4; (d) trigger/boundary token aggregates (`getActiveTagTokenAggregate`, `transform.ts:2282`, already gated on `ctxReduceCallable`, which this mode forces false) — the trigger never runs and its math primes from raw message caches; (e) `ctx_search` — sources are memories, message FTS, commits, compartment chunks, notes; tag rows are not a source; (f) ordinal mapping — reads raw message order, tagger-independent; (g) historian input — raw content only, fingerprints exclude tag state. This is the distinction from reduce-unavailable mode, where drops/emergency/boundary stay live and tags therefore still mint; that rule does NOT carry over.
- Flip-back self-heals: the tagger lazily mints on first observation of untagged wire content (the same mechanism that handles mid-session `ctx_reduce` enablement). Folded-away content is never retroactively tagged; no backfill or migration.

**Markers, and the flip-off unfold consequence (settled — decisions #7 and #8)**
- Primary mechanism: DELETE every MC-owned marker lineage for the session on the off-transition pass. Ownership covers the CURRENT canonical lineage (the 3 deterministic-ID rows written by `compaction-marker.ts:470-546` — compaction part, summary message, summary text part) AND every supported LEGACY MC lineage already recognized by the existing legacy-removal logic (`removeLegacyMarkerLineageRows`, `compaction-marker.ts:471-479`), because upgrade sessions can carry older MC marker shapes. Ownership matching is constrained by MC-specific deterministic IDs/signatures plus session identity; a native row can never match.
- Deletion is transactional per lineage, touches no compartment rows, preserves every native marker row, and is idempotent (absent rows delete as a no-op). It is crash-safe under the delete-then-record protocol. Native marker rows and stored compartment rows are never deleted or rewritten.
- Fallback (unchanged in scope): convert MC-owned rows to inert rows, adopted ONLY if either mixed-ordering fixture contradicts the newest-marker reading.
- Verification route: confirm `filterCompacted` semantics with the OpenCode peer (project rule: OC-internals questions go to peer `OC`) as the design-time check; the fixture tests against an OpenCode-compatible database are the durable guard. Do not re-derive OC internals from our repo.
- Scope of the unfold (corrected): removing MC markers exposes the history hidden SOLELY by MC, stopping at any surviving native compaction boundary. Only in a session with no surviving native marker does this return the full raw session history. On a heavily folded session that expansion can exceed the model window before native compaction reacts; OpenCode recovers via its provider-overflow path (`needsCompaction` on the 400, constraint #5071) — one failed request, then native compaction folds. The flip-off notice AND the docs state this plainly ("the first turn after disabling may trigger one native compaction cycle on long sessions"). MC builds NO mitigation — pre-trimming here would be compaction work in compaction-off mode, the contradiction this mode exists to avoid.
- Transition-pass ordering: OpenCode applies `filterCompacted` BEFORE the transform receives the array, so the pass that performs deletion still sees the truncated history and the unfold takes effect from the NEXT pass onward. The transition pass must NOT attempt to re-expand or re-splice history in-pass.
- Lazy per-session cleanup (accepted limitation): cleanup runs on a session's first pass after the flip. A session never resumed after flip-off keeps its MC marker rows, so its pre-boundary history stays hidden in that session (with no `<session-history>` to compensate, since the mode never renders one) until it is resumed, at which point cleanup runs normally. No sweep, no migration, no background job. Documented.

**Ordering + transitions (binding)**
- Mode transitions are detected via a durable per-session mode record with three logical values: no record, `on`, `off`. Boot resolves the configured mode process-stably; each session reconciles its stored value on its first transform pass. Matching stored and configured values do no transition work.
- NO-RECORD SEMANTICS (binding): a missing record resolves to `on`. Every session predating this feature ran with compaction enabled, so `no record + off` IS the off-transition and runs the full replay-safe off cleanup — this is what guarantees marker cleanup reaches legacy/upgrade sessions instead of orphaning their MC-hidden history.
- `no record + on` → write `on`; no transition work.
- `no record + off` and `on → off` → exactly ONE off-transition per session: delete MC-owned marker lineages (canonical + legacy), clear the `needs_emergency_recovery` latch, clear persisted Channel-2 pending/claimed intent, clear pre-existing `pending_ops` (so queued drop intents cannot survive dormant and apply on flip-back), then emit the flip-off unfold notice out of band. The notice is emitted ONLY when the pass actually cleared something (an MC marker lineage, the latch, a Channel-2 intent, or pending ops); a fresh session whose first-ever run is off-mode with zero MC state writes the record and emits NO notice, so it never claims a transition the user did not make.
- `off → on` → exactly ONE on-transition: write the historian catch-up signal and emit one `/ctx-wrapup` suggestion out of band, CONDITIONED on the historian being runnable; when the historian is disabled the transition writes the record only and emits no suggestion (never advertising an unavailable command).
- Every cleanup operation is idempotent, and the mode record is written only AFTER all transition work completes; a crash before the write causes safe re-execution of the same logical transition. Mutating side effects do not duplicate; notice delivery follows the at-least-once contract above.
- Because the mode is boot-resolved and process-stable, a transition is only ever observed on a session's first pass after a restart that changed the resolved value; there is no in-process flip.
- Storage slot: OQ-FIRSTPASS-STORE must be CLOSED before transition behavior lands — no transition pass may rely on an unverified slot, and exactly-once/crash-safe ordering depends on the slot's write semantics. If a new column is required it is migration-bearing, rides rule #9597, and gives pre-existing rows an unambiguous no-record representation.
- Marker cleanup on flip-off lands WITH the mode gate.
- Boot resolves the mode process-stably (per-process tool registration, constraint #5070); tool registration and TS/rust selection use that frozen value.

**Mode behavior**
- Memory injection MUST survive: a dedicated mutation-direction test proves the `<project-memory>` block injects with compaction off and goes red if the re-gating above ever swallows m[0]/m[1] injection.
- Additive injection stays byte-stable across non-transition passes (m[0]/m[1] cache discipline unchanged); no new per-pass byte churn.
- Emergency/overflow machinery disarms: ≥85% tiered drop, 95% fail-closed block, overflow-recovery latch, both nudge channels. A persisted `needs_emergency_recovery` surviving a flip-off is cleared, not honored.
- Pi: `session_before_compact` is NOT cancelled in this mode (missing this = NO compaction at all on Pi → unbounded context), and no fail-closed path substitutes cancellation. Same resolved flag, same additive-only contract in Pi's context-handler.
- Commands: `/ctx-wrapup`, `/ctx-recomp`, `/ctx-flush` and `/ctx-session-upgrade` refuse with the exact single line `Unavailable: magic-context is in compaction-off mode (compaction.enabled=false).` and perform ZERO side effects — no pending-op drain, no compartment row, no marker write, no `session_meta` mutation. `/ctx-embed` STAYS functional — it backfills embeddings for `ctx_search` (knowledge layer), not compaction.
- `transform_mode: "rust"` + compaction off → the TypeScript transform running in compaction-off mode, with a frozen boot warning (no rust compaction-off contract this cycle; `transform-mode.ts` precedent). Do not call this "reduced mode": `reduced` is reserved for the existing subagent split.
- Fail-closed blocking is inert in this mode BY DESIGN (MC inoperability no longer risks unbounded growth): a thrown or failed transform yields the unmodified input messages, no blocking message, no cancelled request, on BOTH harnesses. Documented in the config description.
- Nudges-off rationale (closed): native compaction (or nothing) is the user's chosen manager; a "context nearly full" warning would be advice about a threshold MC does not act on. Accepted risk documented; a future revisit is one gate + one template, not structural.
- Sidebar: RAW context usage vs the model limit with a mode label. `<pct>` is the raw measurement — wire input tokens ÷ resolved model context limit, i.e. the value MC already persists to `session_meta.last_context_percentage` (which keeps being written in this mode) — NOT a threshold-relative fill; `executeThreshold` must not reach the renderer and the execute-threshold fill % must NOT render. The label reflects the RESOLVED native state: `Context: <pct>% · native compaction` when native compaction is on, `Context: <pct>% · no active compaction` in the no-manager configuration, consistent with the boot advisory (decision #4's rule: render only what something real acts on — that applies to the label as well as the number). Historian and compartment-activity rows hidden; memory + notes rows stay; historical compartments may render only as a static archived count that does not change across passes, never as active reclaimable context.
- Subagent documentation (two arms, selected by the OpenCode peer verification; zero code either way): ask whether `compaction.auto` covers sessions with a `parentID` (threshold check AND provider-overflow `needsCompaction` recovery). Arm A (covered): one paragraph in the mode docs — subagents are managed by native compaction like any session; MC does not reclaim their context in this mode. Arm B (not covered): TOP prominence — a warning box in the mode docs, the `.describe()` line above, and a boot-advisory mention, stating the failure shape (silent empty Task result on provider overflow, issue #270). Both arms also state the additive consequence (subagents receive memory/docs injection but no MC reclaim) and point at the user's mitigation: scope subagent tasks small, or keep `compaction.enabled` on for projects that lean on long subagent runs.
- Rules: schema via Zod + `build-schema.ts` regen (#5679); both dists rebuilt in fence-relevant merges, including any storage migration (#9597); no real git spawns in tests (#8342).


## acceptance_sketch


**Back-compat (widest blast radius)**
- Direct parse of `{}` → `compaction.enabled === true`; `{ compaction: {} }` → `true`; absent block → `true` — asserted directly, not inferred.
- Config with no `compaction` block: transform output, registered tools, conflict results, native-config repair behavior, command behavior, sidebar snapshots and transform-mode selection have zero deltas.
- A running process ignores a config-file change to `false`; a restarted process resolves `false`.
- Accessor exclusivity: a repo-wide check finds no non-schema read of the `compaction.enabled` config path outside `isCompactionEnabled`; pi-plugin and cli import the accessor.

**Conflict matrix and native writers (the inverse-of-intent guard)**
- Call-site continuity: a repo-wide check finds no production call site deciding compaction-conflict behavior from directory alone; plugin boot, `setup-opencode`, `doctor` and `conflict-fixer` each pass the boot-resolved MC config into `detectConflicts`.
- Compaction OFF + OpenCode `compaction.auto=true` (and separately `prune=true`) → `detectConflicts` reports no compaction conflict and `pluginConfig.enabled` remains `true` after `index.ts:147-155`. Asserted on the resolved flag, not on log text.
- Regression: compaction ON + `auto=true` → conflict reported and plugin disabled exactly as today; existing DCP/OMO fixtures retain their current results and fixes in BOTH modes.
- `setup-opencode` in compaction-off mode: `opencode.jsonc` after the run contains the pre-existing `compaction` values byte-for-byte (no `auto=false`, no `prune=false`); dry-run prints no compaction-write intent.
- `fixConflicts` in compaction-off mode: `compaction.auto` is never flipped to `false`. `doctor` in compaction-off mode reports compaction state and mutates zero files.
- MC config fails to load → every writer takes the preserve-existing-native-fields branch and emits a diagnostic.
- Compaction OFF + resolved native `auto=false` → boot advisory and doctor report the no-manager configuration; zero files mutated.

**Project-tier strip (both harnesses)**
- OpenCode only-key case: project `{ compaction: { enabled: false } }` → `enabled` removed, warning names `compaction.enabled`, user-tier value honored, block not deleted wholesale. Sibling case `{ compaction: { enabled: false, futureSibling: 1 } }` → only `enabled` removed, `futureSibling` survives. Both asserted for repo-committed AND locally-edited project files. Pi loader: identical two cases.

**Mode-record storage and transitions**
- OQ-FIRSTPASS-STORE closure is asserted BEFORE transition behavior lands: the chosen durable slot exists and is tested for value domain, the no-record representation for pre-existing rows, initialization path and read/write helpers; a new column carries a migration test under rule #9597.
- Five state cases, each transition running exactly once per session under normal execution: `no record + on`; `no record + off` on a LEGACY session carrying MC state; `no record + off` on a CLEAN new session; `on → off`; `off → on`. Matching on→on / off→off passes are no-ops.
- `no record + off` (legacy): deletes canonical AND legacy MC marker lineages, clears the emergency latch, Channel-2 intent and `pending_ops`, emits the flip-off notice, and writes `off` only afterwards.
- `no record + off` (clean session, zero MC state): writes `off`, changes no rows, and emits NO flip-off notice — asserted explicitly, since a spurious notice would claim a transition the user never made.
- `on → off`: same cleanup set as above, starting from a fixture with non-empty `pending_ops`, an armed `needs_emergency_recovery` latch and a persisted Channel-2 intent; after the pass all three are clear and subsequent compaction-off passes keep `pending_ops` empty.
- `off → on` with historian runnable: exactly one historian catch-up signal and exactly one `/ctx-wrapup` suggestion. `off → on` with historian disabled: record written, no catch-up signal, no `/ctx-wrapup` suggestion.
- Crash safety: inject a failure after each database side effect but before the mode-record commit; the retry converges to the same row state and commits the mode exactly once, with no duplicated mutating side effect. Notice repeats are permitted only in that crash window, per the declared at-least-once contract.
- Flip-off notice text contains the one-cycle warning ("the first turn after disabling may trigger one native compaction cycle on long sessions"); the same wording appears in docs and both quote the same source constant; no MC fold/drop mitigation exists on that path.

**Notices are out of band**
- On every transition pass (both directions) the transform's output message array is structurally identical to a steady-state compaction-off pass: no added or modified message, no synthetic turn, no Channel-1 state written, no Channel-2 pending intent set. The notice is observed only on the out-of-band surface.
- Cardinality: transition notices fire once per session on an uninterrupted pass; the no-manager advisory and rust-downgrade warning fire once per process.
- Mutation direction: route any notice through the message array or the nudge machinery → the structural-diff assertion goes red.

**Marker cleanup and restored history**
- Fixtures against an OpenCode-compatible database: canonical MC marker only; supported LEGACY MC lineage; native-after-MC; MC-after-native. In every case only MC-owned rows are removed, every native row and compartment row is preserved, and exactly the history hidden solely by MC becomes visible.
- Idempotence oracle: run cleanup twice; the second run reports ZERO affected rows and leaves the relevant `message`/`part` row sets, values and ordering unchanged. Whole-file SQLite byte identity is NOT used as the oracle (WAL, journaling and page allocation move without row changes).
- In the mixed-ordering fixtures a surviving native boundary remains authoritative: history before it stays hidden. Only the MC-only heavily folded fixture exposes the complete raw session history.
